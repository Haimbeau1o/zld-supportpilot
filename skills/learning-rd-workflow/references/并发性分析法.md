# 学习型研发工作流：并发性分析法

## 目的

在任务开始前判断哪些 Issue 需要串行，哪些可以并行，以及何时需要创建融合 Issue。

## 分析步骤

### 1. 识别前置基础能力

优先识别是否依赖以下内容：

- 认证与身份上下文
- 核心领域模型
- 数据库主表结构
- 核心 API 协议

如果依赖项还未稳定，默认不要直接并行。

### 2. 识别共享边界

重点检查两个 Issue 是否共享：

- 同一实体模型
- 同一权限边界
- 同一输入输出协议
- 同一条主业务链路

共享边界多，说明并行风险高。

### 3. 判断可并行条件

只有同时满足以下条件，才建议并行：

- 输入输出边界已约定
- 各自修改的核心模型不冲突
- 联调点可控
- 后续已经预留融合 Issue

### 4. 生成执行波次

按“先前置、再主线、后融合、再高层能力”生成 Wave。

### 5. 生成融合建议

出现以下情况时，建议创建融合 Issue：

- 两个并行 Issue 最终接入同一条主链路
- 两个模块需要统一接口、权限或数据结构
- 需要专门留出联调和验收步骤

## 输出模板

```markdown
| Issue | 前置依赖 | 可并行性 | 波次 | 融合建议 |
| --- | --- | --- | --- | --- |
| #3 | #2 | 可与 #5 并行 | Wave 2 | 后续与 #7 融合 |
```
