# 学习型研发工作流

## 概览

把项目推进成“边做边学、边做边沉淀”的工作流，而不是只交付代码。始终同时交付工程结果与学习结果。

## 核心原则

- 先明确用户要“吃透项目”还是只要“尽快交付功能”
- 先做需求澄清、调研和方案对比，再写实现计划
- 先分析 Issue 依赖和并发性，再决定执行顺序
- 先定义融合点，再放行并行开发
- 在关键业务逻辑、边界条件、设计取舍处写中文注释
- 每个 Issue 同时沉淀代码、验证记录和工作文档

## 固定交付物

为每个 Issue 建立独立工作包目录，并固定输出以下 7 件文档：

1. `00-任务卡.md`
2. `01-调研记录.md`
3. `02-方案设计.md`
4. `03-实施计划.md`
5. `04-验证记录.md`
6. `05-工作日志.md`
7. `06-复盘总结.md`

详细清单见：`references/交付物清单.md`

## 工作流

### 第 1 步：识别目标

先判断以下问题：

- 用户是要理解项目，还是只要交付结果
- 本次工作是方法层、业务功能、融合收口、调研，还是复盘
- 当前阶段最重要的是“降低不确定性”还是“推进实现”

### 第 2 步：建立任务卡

先写清：

- 背景与问题
- 目标与范围
- 非目标
- 验收标准
- 前置依赖
- 并发性判断
- 输出物

### 第 3 步：进行调研与方案对比

不要只给结论。必须记录：

- 查了哪些资料
- 比较了哪些候选方案
- 每种方案的优缺点
- 最终为什么做当前选择

### 第 4 步：做并发性分析

对每个 Issue 输出 3 个固定结果：

- `Issue 依赖图`
- `执行波次表`
- `融合 Issue 建议`

使用以下判断顺序：

1. 先找基础前置能力
2. 再找共享核心模型
3. 再找接口和权限边界
4. 最后判断能否并行

如果两个 Issue 共用以下任一内容，默认先视为“不可直接并行”：

- 核心领域模型
- 权限与租户边界
- 同一条主链路的输入输出协议
- 尚未稳定的数据库结构

详细方法见：`references/并发性分析法.md`

### 第 5 步：写实施计划

把工作拆成可执行步骤，明确：

- 涉及文件
- 执行顺序
- 联调点
- 风险点
- 哪些步骤可以并行

### 第 6 步：实现并补中文注释

在以下位置强制补中文注释：

- 关键业务规则
- 边界条件
- 并发控制、超时、重试、幂等
- 设计取舍明显不直观的地方

不要把注释写成逐行翻译；解释“为什么这样做”和“后续维护要注意什么”。

### 第 7 步：验证与复盘

同时记录：

- 自动化验证
- 手工验证
- 边界验证
- 失败与修正
- 本次学到的内容
- 对后续 Issue 的影响

## 并发性分析输出格式

至少输出如下结构：

```markdown
## 依赖关系
- 前置依赖：#2
- 后续依赖：#7

## 并发性判断
- 是否可独立并行：是 / 否
- 可并行对象：#5
- 阻塞点：权限边界尚未稳定

## 融合建议
- 建议融合 Issue：融合：打通工单、知识库与 AI 主链路
```

## 红旗

出现以下想法时，说明流程正在失控：

- “先把功能写出来再补文档”
- “这个 Issue 依赖关系不重要，先做了再说”
- “并行开发以后再看怎么合”
- “中文注释太慢，先不写”
- “调研过程没必要记录，记结论就够了”

## 常见错误

- 把 workitem 文档写成空模板，不记录真实过程
- 把并行判断写成“可并行”，但没有说明接口和边界是否稳定
- 把融合 Issue 当成简单汇总，而不做联调和接口收口
- 把复盘写成流水账，没有抽象出可复用经验
