## RED / GREEN 验证

### 1. 主闭环集成测试

- 测试文件：`internal/app/app_main_loop_test.go`
- 测试名称：`TestNewMainLoopFusionSupportsEndUserFeedbackToKnowledgeCycle`
- 目标：验证“终端用户提问 → unresolved 反馈 → 建单 → AI 工单辅助 → resolved → 知识候选审核入库 → 下次命中新知识”整条主闭环

#### RED 现象

- 初次执行时，终端用户调用 `/api/v1/ai/intakes` 返回 `403 forbidden`
- 失败原因不是测试数据问题，而是真实应用集成路径上的权限缺口：
  - AI intake 在真实应用中通过 `knowledge.Service` 读取已索引 chunk
  - `knowledge.Service.ListIndexedChunks()` 之前复用了知识库后台读权限判断
  - `end_user` 角色没有后台知识读权限，因此被错误拦截

#### GREEN 修复

- 修复文件：`internal/module/knowledge/service.go`
- 修复方式：
  - 不放开原始文档和知识库管理能力
  - 仅对“已发布 chunk 的读取”增加自助服务访问判定
  - 要求调用人属于同租户，且满足：
    - 具备常规知识读写权限，或
    - 具备终端用户自助工单权限（`ticket:self:create` / `ticket:self:read`）
- 结果：测试通过

### 2. 知识层回归测试

## Demo 脚本验证

### 目标

- 让 README 中的 `#28 主闭环演示` 可以真实跑通，作为人工验收与简历演示入口

### 首次失败

- 脚本：`scripts/demo_issue_028_closed_loop.sh`
- 现象：注册阶段 `curl` 报错，JSON body 被 shell 拆词，出现 `Could not resolve host` 等异常
- 根因：`request_json()` 使用数组拼装 curl 参数，但执行时使用了会触发二次拆词的写法，导致带空格、中文的 JSON body 被破坏

### 修复方式

- 保持数组建命令方式不变
- 将执行方式改为 `response="$("${cmd[@]}")"`
- 在脚本中补充中文注释，明确此处是为了避免 JSON body 被 shell 二次拆词

### 复验结果

- 启动服务：`AUTH_SIGNING_KEY=test-signing-key AUTH_TOKEN_TTL_SECONDS=3600 GOCACHE=/tmp/go-build go run ./cmd/api`
- 执行脚本：`BASE_URL=http://127.0.0.1:8080 bash scripts/demo_issue_028_closed_loop.sh`
- 结果：通过
- 关键输出：
  - `knowledge_base_id=kb-1`
  - `ticket_id=ticket-1`
  - `candidate_id=kc-1`
  - `approved_document_id=doc-2`
