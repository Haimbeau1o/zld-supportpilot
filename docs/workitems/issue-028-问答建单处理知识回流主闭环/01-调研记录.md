# 调研记录

## 调研目标

确认 `#28` 到底是“新增业务功能”，还是“融合收口 issue”，并识别最小实现落点。

## 调研结论

### 1. `#28` 是融合收口 issue，不应继续扩领域模型

证据：

- `#25` 已建立统一受理入口
- `#26` 已建立 unresolved feedback -> ticket 的回流能力
- `#27` 已建立 resolved ticket -> candidate -> approved document 的知识沉淀能力

因此 `#28` 的最小合理实现应是：

- 先写跨模块闭环测试
- 只补最小胶水
- 再补 demo 脚本和文档

### 2. 现有链路已经具备主闭环的大部分组件

关键落点：

- `internal/module/ai/service.go`
  - `HandleUnifiedIntake`
  - `SubmitAnswerFeedback`
  - `GenerateTicketAssist`
- `internal/module/knowledge/candidate_service.go`
  - `CreateKnowledgeCandidateFromTicket`
  - `ReviewKnowledgeCandidate`
- `internal/app/app.go`
  - 已把 AI、ticket、knowledge 三个模块接到同一个运行时中

### 3. 当前最需要的是端到端证据，而不是新模块

现有仓库已经有：

- RAG 路由集成测试
- 统一 AI intake / feedback 测试
- 工单 AI assist 测试
- 知识候选审批回写测试

缺的是“一条把这些能力从用户提问串到下次命中的自动化闭环测试”。

## 当前判断
