# 方案设计

## 方案选型

### 方案 A：继续新增一个“闭环 orchestrator” service

优点：

- 看起来统一

缺点：

- 会把本来清晰的模块边界再打散一次
- 只是为了演示而引入新中心层，收益低

### 方案 B：以端到端测试和 demo 脚本作为融合主入口（推荐）

优点：

- 不破坏现有领域边界
- 更贴近真实交付中的“联调与收口”工作方式
- 直接产出可演示、可验证、可讲述材料

缺点：

- 对测试场景设计要求更高

## 推荐结论

采用方案 B：

- 先在 `internal/app/app_test.go` 写主闭环 RED 测试
- 如果 RED 暴露缺口，只补最小胶水代码
- 完成后再新增 demo 脚本与 README 操作文档

## 主闭环场景设计

### 参与角色

- 终端用户：提问并提交 unresolved feedback
- 处理人（agent）：查看工单、调用 AI assist、人工解决、提交知识候选
- 审核人（当前阶段可复用 agent 权限）：审核候选并入库

### 状态流

1. `intake` 创建
2. `feedback unresolved`
3. `ticket created / linked`
4. `ticket assist generated`
5. `ticket resolved`
6. `knowledge candidate pending_review`
7. `knowledge candidate approved`
8. `document ready`
9. `second answer answered`

## 验证策略

### 自动化验证

- `internal/app`：主闭环端到端测试
- 必要时补 `internal/platform/http` 或 `internal/module/ai` 小粒度回归测试

### 手工 / 脚本验证

- 提供 `scripts/demo_issue_028_closed_loop.sh`
- 让整个流程可以通过脚本复现

## 数据策略

- 第一次问答使用“泛化旧知识”保证能答但不够解决
- 第二次问答依赖候选审批后的新知识命中，证明闭环真的生效
