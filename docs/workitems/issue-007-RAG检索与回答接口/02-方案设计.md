# 方案设计

## 设计目标

围绕知识库构建一个最小可用的 RAG 回答接口：已准备好的 chunk 先进入检索层，再由回答层基于检索结果生成带引用的回复。如果检索结果不足以支撑可靠回答，则明确返回降级结果，避免“AI 幻觉”。

## 模块边界

- `internal/module/knowledge`
  - 暴露“列出某知识库 ready chunk”的读取能力
  - 继续负责租户、知识库归属和 chunk 存储边界
- `internal/module/ai`
  - 负责 query 向量化、chunk 检索、分数排序、降级判断、回答生成和引用组装
- `pkg/llm`
  - 继续作为未来真实模型适配入口
- `internal/platform/http`
  - 提供受保护的 AI 回答接口
- `internal/app`
  - 装配 knowledge + ai 服务

## 数据流 / 时序

1. 用户携带令牌调用 AI 回答接口，并指定知识库与问题。
2. AI 服务先通过 knowledge 边界读取当前知识库的可检索 chunk。
3. 检索器将问题与 chunk 内容映射为向量，并按相似度排序。
4. 若最高分低于阈值，则直接返回降级结果与建议，不进入回答生成。
5. 若分数足够，则选取 TopK chunk，构造回答上下文。
6. 回答生成器基于上下文和问题生成答案文本，并携带引用来源。
7. HTTP 层返回 `status / answer / confidence / citations`。

## 接口或数据结构草案

新增 AI 模型：

- `AskKnowledgeQuestionInput`
- `AnswerResult`
- `AnswerStatus`
- `Citation`
- `RetrievedChunk`

新增抽象：

- `ChunkSource`
- `VectorEmbedder`
- `Retriever`
- `AnswerGenerator`

建议接口：

- `POST /api/v1/ai/knowledge/bases/{id}/answers`

请求体：

```json
{
  "question": "VPN 无法连接怎么办？",
  "top_k": 3
}
```

响应体核心字段：

```json
{
  "status": "answered",
  "answer": "...",
  "confidence": 0.81,
  "citations": []
}
```

## 错误处理与边界条件

- 空问题、TopK 非法值应直接返回 400。
- 知识库不存在、无权限访问应沿用现有权限和归属错误语义。
- 没有 ready chunk 或相似度过低时，统一返回 `degraded`，避免编造答案。
- 当前阶段的回答生成先采用模板式生成，后续再无缝接入真实 `llm.Provider`。

## 中文注释计划

以下位置必须写中文注释：

- 为什么当前阶段选择内存向量检索而不是外部向量库
- 为什么低置信度时宁可降级，也不拼接“看起来像答案”的文本
- 为什么 `ai` 模块只消费 `knowledge` 的 ready chunk，而不直接介入文档处理流水线
- 为什么回答接口必须显式返回引用，而不是只返回纯文本
