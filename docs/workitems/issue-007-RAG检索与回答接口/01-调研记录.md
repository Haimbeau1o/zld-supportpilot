# 调研记录

## 调研目标

在不引入外部基础设施的前提下，为当前仓库搭建一个足够真实、又便于讲解的 RAG 问答闭环。

## 调研问题

- 现有 `#6` 已提供哪些可以直接复用的输入边界？
- 检索应放在 `knowledge` 模块里，还是独立到 `ai` 模块更合适？
- “向量检索接入”在当前阶段如何做，既保留真实感，又避免过度依赖外部服务？
- 低置信度降级应在检索层还是回答层决策？

## 资料来源

| 来源 | 链接/位置 | 关注点 | 结论摘要 |
| --- | --- | --- | --- |
| 仓库代码 | `internal/module/knowledge/processing.go` | chunk 和索引边界 | `#6` 已稳定 parser/chunker/indexer 抽象，`#7` 只需消费 ready chunk，不需要回改上传链路 |
| 仓库代码 | `internal/module/knowledge/service.go` | 文档处理状态 | `ready` 文档是天然的 RAG 输入边界，低于该状态不应参与回答 |
| 仓库代码 | `pkg/llm/provider.go` | 大模型抽象 | 已有最小 `Provider` 接口，可为后续真实模型接入留口 |
| Issue 定义 | `#7` | 验收标准 | 重点在“检索抽象、回答引用、低置信度降级”，不是外部服务集成 |
| 后端技能 | `backend-development` | 分层、接口设计、降级策略 | 当前最合适的是 REST API + 模块化服务分层 + 显式错误/降级响应 |

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 方案 A：直接在 `knowledge` 模块里加 `AnswerQuestion` | 实现快，调用链短 | 知识处理与 AI 生成耦合过深，不利于展示模块边界 | 小型 demo | 否 |
| 方案 B：在 `ai` 模块中建立独立 RAG 服务，消费 `knowledge` 的 chunk 边界 | 检索和回答职责清晰；后续替换真实向量库/模型成本低；更适合简历项目展示 | 需要多一层接口设计 | 当前项目目标 | 是 |
| 方案 C：直接接外部向量库 + 真实 LLM API | 真实度更高 | 外部依赖重，不利于稳定测试和离线演示 | 已有完整云资源 | 否 |

## 最终决策

采用方案 B：在 `internal/module/ai` 中新增独立的 RAG 服务，使用内存向量检索和模板式回答生成，先稳定“检索 -> 生成 -> 引用 -> 降级”的业务闭环。

## 决策理由

- 这样最能体现“AI 应用能力 + 传统后端技术栈”的组合价值。
- 用内存向量检索可以在没有外部依赖的情况下，把向量检索抽象和评分逻辑讲清楚。
- 先把引用返回和低置信度降级做好，比追求真实模型调用更适合当前学习和演示目标。
