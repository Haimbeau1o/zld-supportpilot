# 方案设计

## 目标接口

新增统一受理接口：

- `POST /api/v1/ai/intakes`

请求体：

```json
{
  "knowledge_base_id": "kb-1",
  "question": "VPN 无法连接怎么办？",
  "top_k": 3
}
```

响应体：

- 直接回答：

```json
{
  "result_type": "answered",
  "answer_status": "answered",
  "answer": "...",
  "confidence": 0.88,
  "citations": [...]
}
```

- 已升级工单：

```json
{
  "result_type": "ticket_created",
  "answer_status": "degraded",
  "answer": "当前知识库暂无足够依据...",
  "confidence": 0,
  "citations": [],
  "ticket_id": "ticket-1"
}
```

## 领域设计

### 新增模型

- `UnifiedIntakeInput`
- `UnifiedIntakeResult`
- `UnifiedIntakeResultType`

### 统一受理流程

1. 校验 `knowledge_base_id` 与 `question`
2. 复用 `AskKnowledgeQuestion`
3. 若结果为 `answered`
   - 直接返回答案结果
4. 若结果为 `degraded`
   - 根据问题文本生成工单标题与描述
   - 调用 `ticket.Service.CreateTicket`
   - 返回 `ticket_id`

## 关键取舍

- 本阶段不做“已回答但用户仍想转工单”的双态交互，避免把 API 设计做复杂
- 本阶段不写额外 AI intake 审计仓储，统一先靠工单创建事件与接口返回承接
- 标题生成以可读性优先，保留问题前缀，长度过长时裁剪
