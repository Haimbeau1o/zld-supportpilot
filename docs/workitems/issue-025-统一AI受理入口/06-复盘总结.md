# 复盘总结

## 本次学到的内容

- 统一业务入口不一定要重写全部已有能力，很多时候关键是把“已有能力编排成用户视角的单一动作”
- 现有 `AskKnowledgeQuestion` 已天然具备“能否可靠回答”的判定能力，因此统一入口的核心不是更复杂的 AI，而是更清晰的决策与返回结构
- 对这类串行主线功能，先做 service 层判定，再做 HTTP 路由装配，最后补应用层集成测试，是比较稳的节奏

## 关键取舍

- 本阶段只实现“先答后建单”单一路径，不做“先答后让用户二次确认是否转单”的交互扩展
- 自动建单时只回传 `ticket_id` 与降级结果，不额外引入 intake 审计仓储，避免 scope 膨胀
- 工单标题规则保持最小可读性，问题过长时裁剪，优先保证列表展示可用

## 遇到的问题

- 统一入口 service 测试里建单 stub 最初用了值接收，导致无法保留调用痕迹
- HTTP 层最初返回 404，说明问题非常明确：不是业务逻辑错误，而是路由尚未接线
- 集成测试首次失败来自拼接 JSON 方式错误，提醒后续优先用 `fmt.Sprintf` 等更稳定方式组装请求体

## 下次可优化点

- 为统一受理结果增加“建议分类”或“建议优先级”，让自动建单更贴近真实服务台
- 增加“已直接回答但用户仍要升级工单”的二段式 API
- 在 `#26` 中补充统一入口后的用户反馈闭环，把 answered / ticket_created 结果接到回流判断上

## 对后续 Issue 的影响

- `#26` 可以直接基于统一入口结果做“回答是否解决”的反馈回流
- `#27` 可以围绕统一入口创建出来的工单结论继续沉淀知识候选
- `#28` 融合时可围绕“统一入口 -> 自动建单 -> 处理 -> 回流”验证主闭环
