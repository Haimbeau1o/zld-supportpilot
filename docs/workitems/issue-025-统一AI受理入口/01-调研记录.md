# 调研记录

## 现状侦察

### 已有能力

1. `internal/module/ai.Service.AskKnowledgeQuestion`
   - 已支持按知识库检索 chunk
   - 有明确的 `answered / degraded` 结果模型
   - 低置信度时会返回保守降级回答

2. `internal/module/ticket.Service.CreateTicket`
   - 已支持终端用户或处理方创建工单
   - 默认优先级可回落为 `medium`
   - 会记录创建审计事件

3. `internal/platform/http/ai_handler.go`
   - 当前已暴露两个分离入口：
     - `POST /api/v1/ai/knowledge/bases/{id}/answers`
     - `POST /api/v1/ai/tickets/{id}/assist`
   - 已接入统一鉴权与限流框架

### 设计机会

- `AskKnowledgeQuestion` 已天然具备“是否足够回答”的判定基础，不需要重复发明决策逻辑
- `ticket.Service.CreateTicket` 可直接承接低置信度升级场景
- 统一入口可以复用现有 `AIHandler` 与 `routeRuntime`，实现成本可控

## 风险点

- 如果统一入口直接复用现有问答结果，需要避免在“已建单”场景里返回误导性的高置信度回答
- 自动建单时需要有最小标题生成规则，否则问题文本太长会污染工单列表可读性
- 若后续 `#24` 未合并，`#25` 必须作为 stacked PR 保持在 `codex/persistence-foundation` 之上

## 结论

推荐方案：

- 在 `internal/module/ai` 内新增“统一受理”模型与 service 方法
- 决策逻辑只做一层：先调用 `AskKnowledgeQuestion`，若 `answered` 则直接返回；若 `degraded` 则创建工单
- HTTP 层新增单一路由，保持现有问答与 ticket assist 路由不回归
