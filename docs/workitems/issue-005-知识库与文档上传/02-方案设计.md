# 方案设计

## 设计目标

在租户与权限边界稳定的前提下，以最小可用但可扩展的方式建立知识库与文档上传链路，使后续模块只关心“文档属于哪个知识库、原始文件在哪里、处理状态到哪一步”。

## 模块边界

- `internal/module/knowledge`：知识库模型、文档元数据模型、上传状态、仓储接口、存储接口、服务层与内存适配
- `internal/platform/http`：知识库创建、列表、文档上传、文档元数据查询接口
- `internal/app`：装配 knowledge service 与 HTTP routes
- `internal/module/identity`：复用现有身份上下文、租户边界与权限集合

## 数据流 / 时序

1. 已登录用户携带 Bearer Token 访问知识库受保护接口
2. 创建知识库时，服务层根据当前身份写入 `OrganizationID`
3. 上传文档时，请求以 multipart/form-data 方式发送文件
4. 服务层先校验知识库归属和权限，再调用存储接口保存原始文件
5. 文件保存成功后，记录文档元数据与上传状态
6. 后续 #6 的异步文档处理将基于稳定的文档元数据和状态字段继续推进

## 接口或数据结构草案

- `POST /api/v1/knowledge/bases`
- `GET /api/v1/knowledge/bases`
- `POST /api/v1/knowledge/bases/{id}/documents`
- `GET /api/v1/knowledge/bases/{id}/documents`
- `GET /api/v1/knowledge/documents/{id}`

核心模型草案：

- `KnowledgeBase`
- `Document`
- `DocumentStatus`
- `CreateKnowledgeBaseInput`
- `UploadDocumentInput`

建议的最小文档状态集合：

- `uploaded`
- `processing`
- `ready`
- `failed`

## 错误处理与边界条件

- 终端用户当前不具备知识库读写权限，只有客服与租户管理员可管理知识库和上传文档
- 不允许跨租户读取或上传到他人知识库
- 上传文件为空、知识库不存在、存储失败时要返回明确错误
- 当前阶段先把原始文件内容存到内存对象存储适配中，不在本 issue 内处理下载、切块和索引
- 文档元数据必须包含文件名、内容类型、大小、上传人、存储键和状态，避免后续 #6 再回头补基础字段

## 中文注释计划

以下位置必须写中文注释：

- 为什么文档上传挂在知识库之下，而不是做成全局上传口
- 为什么当前阶段先用存储接口抽象与内存适配，为后续 MinIO 接入留边界
- 为什么文档状态从一开始就保留 `processing/ready/failed` 扩展位
- 为什么知识库读写权限统一收敛在服务层而不是只依赖 HTTP 层
