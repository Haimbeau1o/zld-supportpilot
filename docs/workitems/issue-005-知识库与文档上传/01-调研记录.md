# 调研记录

## 调研目标

为 `ZLD SupportPilot` 选择一套适合当前 MVP 阶段的知识库与文档上传实现方式，在保证后续异步解析与 RAG 可扩展性的同时避免过早把切块、索引和检索耦合进主线。

## 调研问题

- 知识库上传阶段是否需要真实对象存储接入，还是先做存储接口抽象？
- 文档上传接口应该直接上传到“全局文档入口”，还是明确挂在知识库之下？
- 文档状态应该只记录“已上传”，还是从一开始就保留可扩展的处理状态字段？

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 直接接真实 MinIO | 更接近最终形态 | 本地环境与测试依赖变重，当前阶段易受外部环境阻塞 | 基础设施已稳定 | 否 |
| 存储接口抽象 + 内存适配 | 快速稳定上传与元数据边界，便于 TDD | 后续仍需补真实对象存储实现 | 当前阶段 | 是 |
| 文档上传挂在知识库之下 | 绑定关系明确，后续检索范围更清晰 | 路由略多一层 | 知识库是主要容器 | 是 |
| 全局文档上传接口再回填知识库 ID | 路由更少 | 上传关系容易变模糊，后续融合复杂 | 知识库概念较弱时 | 否 |
| 文档只记录 `uploaded` 状态 | MVP 简单 | 后续引入解析 / 失败状态要改模型 | 没有后续异步处理时 | 否 |
| 文档从一开始就保留处理状态字段 | 为 #6 留稳定扩展位 | 需要先定义最小状态集合 | 后续会有异步链路 | 是 |

## 最终决策

当前阶段采用：`知识库容器 + 文档元数据模型 + 存储接口抽象 + 内存适配 + 可扩展上传状态字段`。

## 决策理由

这样可以先稳定“知识库存什么、文档如何上传、元数据如何追踪、后续异步处理从哪里接入”这些主链路边界，让 #6 和 #7 在已有上传链路之上扩展，而不是反过来驱动主模型返工。
