# 复盘总结

## 本次学到的内容

- 知识链路的主线不是一开始就做切块和检索，而是先稳定“文档归属到哪个知识库、原始文件在哪里、状态是什么”这几个基础事实
- 把知识库读写权限和租户归属判断放在服务层，而不是只写在 HTTP 层，才能保证未来 worker、检索服务和内部调用共用一套边界
- 上传状态从一开始就保留 `processing/ready/failed` 扩展位，可以显著减少后续 #6 反向修改主模型的概率

## 关键取舍

- 选择知识库容器 + 文档元数据模型，而不是做成全局松散文档入口
- 选择存储接口抽象 + 内存适配，而不是直接接真实 MinIO
- 选择把上传接口挂在知识库之下，而不是单独开放全局上传接口
- 在 HTTP 测试中直接使用签发令牌构造同租户身份，把验证焦点放回知识链路本身

## 遇到的问题

- 初始 app 和 router 结构主要面向认证与工单，knowledge 接入后需要继续把路由装配能力演进成可承载多模块的统一入口
- 当前 multipart 上传测试如果过度追求真实对象存储，会让测试目标偏离“上传边界是否稳定”本身

## 下次可优化点

- 为跨租户访问、存储失败注入和无读权限访问补更完整的 HTTP 级测试
- 在 #6 中把异步处理状态更新、失败重试和元数据扩展挂到已稳定的文档模型上
- 后续真实 MinIO 接入时补对象下载、校验和和清理策略

- #7 的检索与回答链路将依赖本 issue 暴露的知识库边界和文档元数据入口
