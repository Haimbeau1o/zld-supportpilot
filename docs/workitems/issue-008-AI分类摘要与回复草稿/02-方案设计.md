# 方案设计

## 设计目标

在不改变工单主数据自动化行为的前提下，为处理方提供一个统一的 AI 辅助接口。该接口基于工单基础信息、协作时间线和知识库检索结果，生成分类建议、处理摘要与回复草稿，并把本次 AI 结果作为内部记录写入工单时间线，确保 AI 输出可追踪但不越权执行。

## 模块边界

- `internal/module/ticket`
  - 继续负责工单读取、时间线读取、内部备注写入和权限边界
- `internal/module/ai`
  - 新增 ticket assist 服务
  - 负责组装工单上下文、复用现有 RAG 能力、生成分类建议 / 摘要 / 回复草稿
- `internal/platform/http`
  - 暴露受保护的 AI 工单辅助接口
- `internal/app`
  - 装配 ticket + ai 服务

## 数据流 / 时序

1. 客服携带令牌调用 AI 工单辅助接口，并指定工单 ID 与知识库 ID。
2. AI ticket assist 服务先读取工单详情和工单时间线。
3. 服务将工单标题、描述与最近协作内容拼接为 AI 分析上下文。
4. 服务复用现有知识库问答 / 检索能力获取知识增强答案与引用。
5. 服务基于工单上下文 + 检索结果生成三类输出：分类建议、处理摘要、回复草稿。
6. 服务把本次 AI 输出格式化为一条内部备注，写回 ticket 时间线，作为 AI 执行记录。
7. HTTP 层返回结构化建议与记录 ID；调用方可人工采纳，但系统不会自动改工单主数据。

## 接口或数据结构草案

建议新增接口：

- `POST /api/v1/ai/tickets/{id}/assist`

请求体：

```json
{
  "knowledge_base_id": "kb-1"
}
```

响应体核心字段：

```json
{
  "category_suggestion": "network",
  "summary": "...",
  "reply_draft": "...",
  "citations": [],
  "recorded_comment_id": "comment-1"
}
```

建议新增 AI 模型：

- `GenerateTicketAssistInput`
- `TicketAssistResult`
- `TicketCategorySuggestion`
- `TicketSummary`
- `ReplyDraft`

## 错误处理与边界条件

- 空 `knowledge_base_id` 直接返回 400。
- 工单不存在、无权限访问时沿用 ticket 的错误语义。
- 只有具备工单写权限的处理方可触发该接口。
- 若知识检索置信度不足，回复草稿中应明确体现“建议转人工深入排查”，但摘要仍可基于工单信息生成。
- AI 输出仅作为建议返回并写入内部备注，不自动修改 `ticket.Category` 或公开回复用户。

## AI 执行记录设计

当前阶段不新增独立 `AIRecord` 仓储，而是复用 `TicketCommentTypeInternalNote`：

- 优点：复用已有时间线、权限和可见性边界
- 约束：内部备注内容需要结构化格式，便于后续检索和人工阅读
- 记录内容建议包含：触发人、知识库、分类建议、摘要、回复草稿、引用来源、降级说明

## 中文注释计划

以下位置必须写中文注释：

- 为什么 `#8` 选择“建议型输出”而不是自动执行
- 为什么 AI 执行记录先复用内部备注，而不是立即新增独立表
- 为什么处理方可触发、终端用户不可触发
- 为什么当知识置信度不足时，仍允许返回摘要，但回复草稿必须显式降级
