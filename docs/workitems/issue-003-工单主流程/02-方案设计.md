# 方案设计

## 设计目标

在租户与权限边界稳定的前提下，以最小可用但可扩展的方式建立工单主流程，使后续模块只关心“当前用户能看哪些工单、能对工单执行哪些主动作”。

## 模块边界

- `internal/module/ticket`：工单领域模型、状态流转规则、仓储接口、服务层与内存适配
- `internal/platform/http`：工单创建、列表、详情、指派、状态流转接口
- `internal/app`：装配 ticket service 与 HTTP routes
- `internal/module/identity`：复用现有身份上下文、租户边界与权限集合

## 数据流 / 时序

1. 已登录用户携带 Bearer Token 访问工单受保护接口
2. 鉴权中间件从令牌恢复 `IdentityContext`
3. 创建工单时，服务层根据当前身份写入 `OrganizationID`、`RequesterID` 与默认初始状态
4. 查询工单时，终端用户只能看自己的工单；客服与租户管理员可以看租户内工单
5. 指派或状态流转时，服务层先校验租户边界和权限，再校验状态机规则
6. 后续 #4 的评论与审计事件将挂载在稳定的工单主模型和动作入口之上

## 接口或数据结构草案

- `POST /api/v1/tickets`
- `GET /api/v1/tickets`
- `GET /api/v1/tickets/{id}`
- `POST /api/v1/tickets/{id}/assign`
- `POST /api/v1/tickets/{id}/status`

核心模型草案：

- `Ticket`
- `TicketStatus`
- `TicketPriority`
- `CreateTicketInput`
- `ListTicketsInput`
- `AssignTicketInput`
- `TransitionTicketStatusInput`

建议的最小状态集合：

- `open`
- `in_progress`
- `resolved`
- `closed`

## 错误处理与边界条件

- 终端用户只能创建、查看自己的工单，不能给其他人的工单改状态或重新指派
- 客服与租户管理员可以查看租户内工单，并执行指派与状态变更
- 不允许跨租户读取或修改工单
- 不允许非法状态流转，例如 `closed -> in_progress`
- 当前阶段先把 `AssigneeID` 视为工单主字段，但不在本 issue 内做复杂成员校验，避免过早把 #3 和更完整的组织管理耦合在一起
- 评论、审计与 AI 相关字段不进入本 issue 的主模型，避免职责膨胀

## 中文注释计划

以下位置必须写中文注释：

- 工单状态机为何采用显式流转规则，而不是自由更新字符串
- 终端用户与客服 / 管理员在查询范围上的差异
- 指派与状态流转为什么拆成独立动作接口
- 当前阶段为什么先用内存仓储和最小字段集合，为后续 #4 留出扩展位
