# 复盘总结

## 本次学到的内容

- 工单主流程的核心不是把所有字段一次做全，而是先稳定“谁能看、谁能改、状态如何流转”这三个边界
- 把查询范围和动作权限放在服务层，而不是只写在 HTTP 层，才能保证未来增加 CLI、任务队列或内部调用时不出现权限漂移
- 对于后续会接入审计和 AI 的模块，显式状态机比自由字符串更新更容易做验证和扩展

## 关键取舍

- 选择显式状态机，而不是自由字符串状态
- 选择 `assign` 与 `status` 两个动作型接口，而不是单一大而全的更新接口
- 选择 interface-first + 内存适配，先稳定主模型和权限边界，再引入数据库
- 在 HTTP 测试中直接签发同租户身份令牌，避免把工单主流程测试过早绑死到成员管理能力

## 遇到的问题

- 初始路由层只支持认证依赖，ticket 路由接入后需要一个能同时承载多模块依赖的装配结构
- 当前 identity 模块还没有“同租户多成员邀请 / 加入”能力，如果直接沿着注册链路构造多角色测试，会把 issue #3 的测试目标污染掉

## 下次可优化点

- 为跨租户拒绝和无写权限拒绝补更完整的 HTTP 级回归测试
- 在 ticket 数据层引入数据库适配后，补列表筛选和分页能力
- 在 #4 中把评论和审计事件挂到已经稳定的主动作入口上，而不是反向修改主模型

- #4 将直接复用本 issue 输出的工单主模型、状态机和动作入口
- #8 的 AI 分类、摘要和回复草稿将依赖本 issue 暴露的稳定工单主链路
