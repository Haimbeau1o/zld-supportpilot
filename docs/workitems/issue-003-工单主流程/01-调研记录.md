# 调研记录

## 调研目标

为 `ZLD SupportPilot` 选择一套适合当前 MVP 阶段的工单主流程实现方式，在保证后续可扩展性的同时避免过早把协作、审计和 AI 能力耦合进主线。

## 调研问题

- 工单状态应该采用自由字符串，还是显式状态机？
- 工单主流程阶段应该使用统一更新接口，还是把“指派”和“状态流转”拆成显式动作？
- 当前阶段应该直接做数据库模型，还是先沿用 interface-first + 内存适配？

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 自由字符串状态 + 通用更新接口 | 开发快、接口少 | 状态规则分散，后续难测试和审计 | 极小型内部工具 | 否 |
| 显式状态枚举 + 专用状态流转动作 | 规则集中、测试清晰、便于后续接审计 | 需要先设计状态机 | 有后续协作与 AI 能力的系统 | 是 |
| 单一 `PATCH /tickets/{id}` 处理所有变更 | 接口统一 | 指派和流转语义容易混在一起 | 字段简单、规则弱 | 否 |
| `assign` 与 `status` 拆成显式动作接口 | 意图清晰，便于做权限校验和审计挂点 | 路由数量略多 | 需要清晰动作边界的服务台 | 是 |
| 直接做数据库持久化 | 更接近最终形态 | 当前仓库还未建立 ticket 数据层与迁移体系 | 数据层已稳定 | 暂缓 |
| interface-first + 内存适配 | 能快速稳定模型和服务边界，利于 TDD | 后续仍需接数据库 | 当前阶段 | 是 |

## 最终决策

当前阶段采用：`显式状态机 + 动作型工单 API + interface-first 的内存适配实现`。

## 决策理由

这样可以先把“工单是什么、谁能看、谁能改、状态如何流转”这些主链路边界稳定下来，让 #4 的协作与审计只是在已稳定模型之上扩展，而不是反过来牵动主流程重构。
