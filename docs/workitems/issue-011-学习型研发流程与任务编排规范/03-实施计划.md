# 实施计划

## 目标拆解

| 步骤 | 工作项 | 预期输出 | 依赖 | 是否可并行 |
| --- | --- | --- | --- | --- |
| 1 | 建立模板目录 | `docs/templates/*` | 无 | 是 |
| 2 | 建立协作文档 | `docs/coordination/*` | 步骤 1 | 是 |
| 3 | 建立通用 skill | `skills/learning-rd-workflow/*` | 步骤 1 | 是 |
| 4 | 建立项目 skill | `skills/zld-supportpilot-delivery/*` | 步骤 1 | 是 |
| 5 | 更新仓库规范 | `README.md` `CONTRIBUTING.md` `.github/*` | 步骤 1~4 | 否 |
| 6 | 输出 Issue 依赖分析 | `docs/coordination/*` | 步骤 2~4 | 否 |

## 涉及文件

- `README.md`
- `CONTRIBUTING.md`
- `.github/ISSUE_TEMPLATE/*`
- `.github/PULL_REQUEST_TEMPLATE.md`
- `docs/templates/*`
- `docs/coordination/*`
- `docs/workitems/issue-011-学习型研发流程与任务编排规范/*`
- `skills/*`

## 执行顺序

先补模板和协作文档，再补 skill，最后再去改 GitHub 的 Issue / PR 流程。

## 风险点

- 规则过多导致后续执行负担过重
- issue 依赖分析如果维护不及时，会很快失真

## 联调点 / 融合点

- 通用 skill 与项目 skill 的输出格式必须一致
- 仓库模板、skill 与 GitHub 模板必须统一
