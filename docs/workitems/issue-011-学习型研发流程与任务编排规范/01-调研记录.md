# 调研记录

## 调研目标

为 `ZLD SupportPilot` 建立一套可复制、可追踪、可学习的研发流程，而不是仅仅补功能。

## 调研问题

- 如何让每个 Issue 既有工程交付，也有学习沉淀？
- 如何让 skill 不只是说明文，而是具备任务编排能力？
- 如何分析现有 Issue 的串行与并行关系？

## 资料来源

| 来源 | 链接/位置 | 关注点 | 结论摘要 |
| --- | --- | --- | --- |
| `superpowers:brainstorming` | 本地 skill | 如何把想法收敛为设计 | 先确定目标，再逐段验证 |
| `superpowers:writing-skills` | 本地 skill | 如何系统化地写 skill | skill 要有触发条件、反模式、固定输出 |
| 当前仓库 README / CONTRIBUTING / Issues | 本仓库 | 当前流程缺什么 | 缺少中文规范、研究沉淀、依赖分析 |

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 只补功能，不补方法层 | 快 | 很快失去上下文，难以学习 | 赶工 | 否 |
| 只写文档，不固化 GitHub 流程 | 成本低 | 约束力弱，容易流于形式 | 小型私有项目 | 否 |
| 文档 + Skill + GitHub 流程一起建立 | 规范完整，可持续复用 | 前期投入较高 | 学习型项目、长期项目 | 是 |

## 最终决策

采用“仓库内模板 + 双层 skill + GitHub 中文流程”的组合方案。

## 决策理由

这样既能保留仓库内的完整沉淀，也能把方法论抽象成 skill，在未来项目中复用。
