# 方案设计

## 设计目标

让后续所有 Issue 在开始前就明确：依赖关系、并发性、文档路径、研究路径、验证方式与融合策略。

## 模块边界

- `docs/templates`：规范每个 Issue 的固定产物
- `docs/coordination`：维护全局依赖和执行波次
- `docs/workitems`：按 Issue 保存工作包
- `skills/learning-rd-workflow`：方法论 skill
- `skills/zld-supportpilot-delivery`：项目上下文 skill

## 数据流 / 时序

1. 创建或调整 Issue
2. 在 `docs/coordination` 中判断其依赖和波次
3. 基于模板创建 `docs/workitems/issue-xxx-主题`
4. 完成调研、设计与实施计划
5. 实现代码并补充中文注释
6. 完成验证记录和复盘总结
7. 如涉及多个并行 Issue，则进入融合 Issue 收口

## 接口或数据结构草案

本 Issue 主要输出文档和流程，不涉及业务接口。

## 错误处理与边界条件

- 如果某个 Issue 范围过大，先拆分为主线 / 并行 / 融合
- 如果两个 Issue 表面可并行，但共享核心模型，则先约定边界再并行
- 如果文档规范更新，必须同步修改 skill 和 GitHub 模板

## 中文注释计划

本阶段主要是文档和 skill，不涉及复杂业务代码。后续代码实现阶段会要求在业务规则、边界条件、并发逻辑和设计取舍处补中文注释。
