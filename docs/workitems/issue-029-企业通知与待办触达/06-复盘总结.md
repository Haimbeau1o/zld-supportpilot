# 复盘总结

## 为什么 `#29` 适合作为并行 issue

通知触达虽然会挂在工单与 AI 的关键链路上，但它本质上是“旁路增强能力”，不改变主链路的核心状态机和数据结构。因此它适合作为并行 issue 推进：

- 依赖的基础工单 / AI 能力已经稳定
- 实现时更多是在已有服务挂接通知发布点
- 对后续 `#30` 的发布、审计、运营视角有明显支撑作用

## 这次实现的价值

### 1. 项目更接近真实内用系统

有了通知之后，系统不再只是“接口存在”，而开始具备主动触达能力：

- 坐席被分派时可以收到提醒
- 请求人能感知状态变化
- AI 升级场景能被外部集成感知

这让系统更像真实会被内部团队使用的服务台，而不是纯演示 API。

### 2. 关键取舍是“最佳努力”，不是“强一致”

本次明确没有把通知视为主事务的一部分，而是采用最佳努力旁路发送：

- 业务成功优先
- 通知失败不回滚业务主数据
- 渠道错误通过返回 error / 日志记录暴露出来

对于当前 M4 阶段，这是更合理的复杂度选择。

### 3. 收件人解析是一个真实工程问题

通知看似只是“发消息”，但真正落地时第一步不是渠道，而是“发给谁”。这次通过给 `identity` 补 `FindByID` / `GetUser`，把用户邮箱解析链路打通，也让 app 装配更接近真实系统。

## 当前边界

本次仍有意保留了若干边界：

- 邮件默认仍走日志 sender，而非正式 SMTP
- Webhook 不做重试 / 持久化 / 死信处理
- 没有引入消息中心页面
- 没有做企业 IM Bot 双向会话

这些都符合当前 issue 的“最小可用通知触达”目标。

## 对 `#30` 的支撑

`#29` 完成后，`#30` 可以基于它继续做更完整的内测交付能力：

- Webhook / 日志与审计事件联动
- 在运营指标中统计升级率、通知触发量等数据
- 在 runbook 里给出对外演示与联调方式

## 结论

`#29` 体现的是一个典型的架构能力：在不破坏主流程边界的前提下，为系统补上真实业务需要的“触达层”。这类能力非常适合作为简历项目里“AI 应用 + 传统后端 + 工程化收口”的证明点。
