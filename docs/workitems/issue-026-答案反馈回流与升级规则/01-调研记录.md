# 调研记录

## 调研目标

确认 `#26` 应该复用哪些既有能力、在哪些位置扩展模型，以及哪些部分必须先做持久化才能让反馈闭环成立。

## 调研范围

- `internal/module/ai/model.go`
- `internal/module/ai/service.go`
- `internal/platform/http/ai_handler.go`
- `internal/module/ticket/*`
- `internal/platform/persistence/schema.sql`
- `internal/app/app.go`
- `docs/workitems/issue-025-统一AI受理入口/*`

## 关键发现

### 1. `#25` 已经具备统一受理能力，但没有可追踪的 intake 记录

当前 `HandleUnifiedIntake` 会直接返回：

- `answered`
- `ticket_created`

但返回结构里没有 `intake_id`，也没有把本次受理结果沉淀到 repository。没有 intake 主记录，就无法把用户后续反馈稳定地绑定到一次具体受理结果。

### 2. `ticket.Service.CreateTicket` 可以直接复用为升级动作

AI 模块当前已经通过 `TicketWorkspace.CreateTicket` 在低置信度时自动建单。因此 `#26` 在 `unresolved` 场景下不需要新造一套升级基础设施，直接复用现有工单创建边界即可。

### 3. 应用层已经有 memory / postgres 双装配，AI 模块当前缺失 repository 实现

`internal/app/app.go` 已经形成统一装配模式：

- memory 模式：内存仓储直接启动
- postgres 模式：启动时自动跑 schema，再注入各模块 postgres repository

因此 `#26` 最合适的做法是在 `internal/module/ai` 中补齐：

- intake repository
- feedback repository
- postgres repository
- memory repository

这样可以无缝挂入现有装配结构。

### 4. 统计接口应视为后台运营能力，而不是终端用户能力

Issue 里要求“后台可看到反馈统计”，所以 stats API 需要放在已登录能力下，并限制为具备后台读权限的角色使用。当前最贴近的权限边界是 `ticket:read`，`agent / tenant_admin` 都具备，而终端用户不具备。

### 5. 升级规则需要防止重复建单

如果一次 intake 已经：

- 在 `#25` 阶段直接建过单，或
- 在首次 `unresolved` 反馈时已经补建过单

那么后续重复提交 `unresolved` 反馈时，不应该继续重复建单，而应该返回已有关联工单。

## 设计推论

- `#26` 需要扩展 `UnifiedIntakeResult`，返回 `intake_id`
- 需要新增 intake 持久化模型，作为 feedback 的锚点
- 需要新增 feedback 提交与统计 service 方法
- 需要在 intake 记录中保留“原始工单关联”和“反馈升级后补建的工单关联”
- 当前阶段可先采用确定性升级规则：`unresolved` 直接建单；后续再扩展为“建议升级 / 确认升级”双轨策略

## 结论

`#26` 不是单纯再加一个 API，而是要把 `#25` 的“瞬时返回结果”升级为“可追踪、可反馈、可运营统计”的业务记录。
