# 实施计划

## 实施顺序

1. 为 intake / feedback service 补 RED 测试
2. 为 memory / postgres repository 补最小实现
3. 为 HTTP feedback / stats API 补 RED 测试并实现
4. 更新 app 装配、schema 与集成测试
5. 跑全量验证并同步 README / 工作文档

## 串并行判断

### 串行部分

- intake 主记录模型 → feedback service → HTTP API → app 装配
- 原因：后面的能力都依赖前面先把数据锚点建立起来

### 可并行部分

- 文档沉淀
- README 更新
- postgres repository 测试补充

### 融合点

- service 与 repository 对齐后统一跑 `go test -count=1 ./...`
- GitHub issue / PR 描述基于验证结果统一更新

## 里程碑

- M1：intake / feedback 领域模型稳定
- M2：feedback API 与 stats API 可用
- M3：memory / postgres 双模式验证通过
- M4：PR 与 issue 同步完成
