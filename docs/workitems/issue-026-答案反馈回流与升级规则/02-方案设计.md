# 方案设计

## 目标接口

### 1. 扩展统一受理返回

`POST /api/v1/ai/intakes`

在 `#25` 的返回基础上新增：

- `intake_id`

示例：

```json
{
  "intake_id": "intake-1",
  "result_type": "answered",
  "answer_status": "answered",
  "answer": "请先重置 VPN 客户端，再重新登录。",
  "confidence": 0.83,
  "citations": []
}
```

### 2. 提交反馈接口

`POST /api/v1/ai/intakes/{id}/feedback`

请求体：

```json
{
  "status": "unresolved",
  "comment": "按步骤操作后仍然无法连接"
}
```

响应体：

```json
{
  "feedback_id": "fb-1",
  "intake_id": "intake-1",
  "status": "unresolved",
  "ticket_action": "ticket_created",
  "ticket_id": "ticket-2"
}
```

### 3. 反馈统计接口

`GET /api/v1/ai/feedback/stats`

响应体：

```json
{
  "total": 12,
  "resolved": 7,
  "unresolved": 3,
  "inaccurate": 2
}
```

## 领域设计

### intake 主记录

新增 `UnifiedIntakeRecord`，保存：

- `id`
- `organization_id`
- `requester_id`
- `knowledge_base_id`
- `question`
- `result_type`
- `answer_status`
- `answer`
- `confidence`
- `ticket_id`
- `escalated_ticket_id`
- `created_at`
- `updated_at`

用途：

- 作为反馈提交的锚点
- 避免重复建单
- 为后续 `#28` 的联调提供统一业务记录

### feedback 记录

新增 `AnswerFeedback`，保存：

- `id`
- `intake_id`
- `organization_id`
- `actor_id`
- `status`
- `comment`
- `ticket_action`
- `ticket_id`
- `created_at`
- `updated_at`

### 状态与动作

反馈状态：

- `resolved`
- `unresolved`
- `inaccurate`

升级动作：

- `none`
- `ticket_created`
- `ticket_existing`

## 升级规则

### 规则 1：`resolved`

- 仅记录反馈
- 不创建工单

### 规则 2：`inaccurate`

- 仅记录反馈
- 不自动建单
- 作为后续知识修订和答案质量统计输入

### 规则 3：`unresolved`

- 若 intake 在受理阶段已经创建过工单，则直接返回现有 `ticket_id`
- 若 intake 在反馈阶段已经补建过工单，则返回该 `ticket_id`
- 若 intake 当前没有任何关联工单，则自动创建工单并回写 `escalated_ticket_id`

## 权限设计

- 提交反馈：要求登录，并且反馈人必须属于同一租户
- 查看反馈统计：要求具备后台读权限，当前以 `ticket:read` 作为最小权限边界

## 持久化设计

新增两张表：

- `ai_unified_intakes`
- `ai_answer_feedbacks`

其中 `ai_answer_feedbacks` 增加 `(intake_id, actor_id)` 唯一约束，保证同一用户对同一次 AI 结果只保留一份最新反馈。

## 关键取舍

- 本阶段不做 feedback 审批流，只做确定性规则，确保闭环先可用
- 本阶段不把 citations 持久化，避免为统计场景引入额外复杂度
- 本阶段统一采用“未解决直接建单”的策略，后续如需“仅建议升级”，再在 `#28` 扩展策略开关
