# 调研记录

## 调研目标

在不引入外部观测平台和分布式基础设施的前提下，为当前仓库补齐一套可讲清楚、可本地验证、又符合真实后端叙事的工程化能力。

## 调研问题

- 当前 HTTP 入口在哪里，最小侵入的观测插入点是什么？
- 请求日志如果要带上用户 / 组织信息，应该放在鉴权前还是鉴权后？
- 指标暴露应该选完整 Prometheus 格式，还是先做项目内自解释的 JSON 快照？
- 当前项目仍是单进程内存实现，限流应该做到什么程度才既真实又不过度设计？
- 发布 / 演示文档应该补哪些内容，才能帮助自己把项目讲透？

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 方案 A：直接接入 OpenTelemetry + Prometheus | 观测能力完整，技术名词更“高级” | 依赖重，配置复杂，当前仓库没有对应基础设施，反而会削弱可控性 | 已有现成监控栈或真实部署环境 | 否 |
| 方案 B：基于标准库做请求 ID、结构化日志、内存指标快照和进程内令牌桶限流 | 实现可控、便于测试、适合当前单机 demo、讲解成本低 | 不具备真正的分布式链路追踪与跨实例限流 | 当前项目阶段 | 是 |
| 方案 C：只补 README，不做代码级观测与限流 | 成本最低 | 工程真实度不足，无法体现后端质量与架构取舍 | 仅做静态作品展示 | 否 |

## 最终决策

采用方案 B：保持标准库优先，在 HTTP 层引入请求 ID、结构化访问日志、基础指标快照和进程内令牌桶限流，并通过 README / 工作文档把演示路径补齐。

## 决策理由

- 这样最符合当前仓库“学习型工程 + 可讲清楚”的目标，既展示工程能力，又避免引入无法稳定演示的外部依赖。
- 请求 ID 可以作为当前阶段“最小链路追踪锚点”，足以把接口调用、日志定位和指标观察串起来。
- 当前系统仍是单进程内存实现，使用进程内限流既合理，也符合“不要为了炫技而过度上设施”的架构判断。
- 用 JSON 指标快照比强行兼容完整 Prometheus 文本更适合当前阶段：人可直接读，测试也更容易写。
