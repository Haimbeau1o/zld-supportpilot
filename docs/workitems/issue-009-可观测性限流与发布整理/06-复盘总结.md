# 复盘总结

## 本次学到的内容

- 工程化收尾不一定要靠完整外部平台，单机 demo 同样可以用“请求 ID + 结构化日志 + 指标快照 + 进程内限流”建立完整叙事。
- 如果希望访问日志带上身份信息，中间件顺序必须围绕鉴权边界设计，而不是简单地在最外层包一层日志就结束。
- 在学习型项目里，把验证命令、演示步骤和取舍理由写进文档，和写代码本身同样重要。

## 关键取舍

- 放弃直接接入 OpenTelemetry / Prometheus，转而采用标准库优先的最小实现，保证本地可控与可测试。
- 限流只覆盖登录、文档上传、文档重试和 AI 问答，而不是对全部接口做一刀切保护。
- 保持业务 handler 不改，把主要改动集中在 `router.go` 和中间件层，减少回归面。

## 遇到的问题

- 需要在“拿到身份上下文”和“记录被拒绝请求”之间平衡中间件顺序；
- 需要保证新增观测能力不会把测试输出刷满，因此在 `test` 环境下默认丢弃运行期访问日志；
- 计划文档最初预估会改 `app.go`，实际实现后发现统一装配点放在 `router.go` 更合适，后续已回填文档保持一致。

## 下次可优化点

- 如果后续进入多实例部署，可把限流升级为 Redis / Lua 方案，并接入共享指标采集；
- 可以继续引入 panic recovery、慢请求阈值告警和更细粒度的指标标签；
- 可以为未鉴权请求单独补一层匿名观测，以覆盖更多失败路径。

## 对后续 Issue 的影响

- `#8` 等 AI 能力已具备最小工程化观测与保护边界，后续演示更完整；
- 后续如果新增真实模型接入或外部存储，也有了统一的请求关联与指标基座可复用；
- 本次文档沉淀可作为后续“工程化收尾”类 Issue 的参考样例。
