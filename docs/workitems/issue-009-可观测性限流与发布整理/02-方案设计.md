# 方案设计

## 设计目标

在不打断现有业务主链路的前提下，把 `zld-supportpilot` 的 HTTP 入口从“能响应请求”提升到“能关联、能观察、能保护、能演示”。这里的核心不是一次性堆满监控技术，而是建立一套最小但完整的工程化闭环：每个关键请求都有请求 ID、访问日志、基础指标；每个高成本或高风险入口都有明确限流边界；每条能力都能通过文档和测试解释清楚。

## 模块边界

- `internal/platform/config`
  - 增加限流相关配置项
  - 保持默认值对本地开发友好
- `internal/platform/http`
  - 负责请求 ID 注入与读取
  - 负责结构化访问日志与 HTTP 指标记录
  - 负责暴露只读指标接口
  - 负责对选定高成本路由施加限流中间件
  - 继续保持现有 handler 业务逻辑不变，把改动尽量约束在装配层
- `internal/app`
  - 继续复用 `NewMuxWithRouteDependencies`，无需额外增加 server 包装层
- `README.md`
  - 负责补齐观测、限流和演示说明

## 数据流 / 时序

### 请求关联与访问日志

1. 请求进入已注册路由；
2. `requestIDMiddleware` 优先复用 `X-Request-ID`，否则生成新的请求 ID；
3. 请求 ID 写入上下文并回写到响应头；
4. 鉴权成功的受保护路由进入观测中间件；
5. 观测中间件在响应结束后记录结构化日志：包含 `request_id`、`route`、`method`、`path`、`status`、`duration_ms`，以及可选的 `user_id` / `organization_id`；
6. 同时更新进程内 HTTP 指标快照。

### 限流

1. 对“高成本或高风险”路由显式挂载限流中间件；
2. 公共登录接口按客户端地址限流，受保护高成本接口优先按 `organization_id:user_id` 限流；
3. 令牌桶允许请求通过时继续执行后续 handler；
4. 令牌不足时直接返回 `429 Too Many Requests`，并附带 `Retry-After`；
5. 被拒请求同样进入访问日志和状态码统计，限流命中次数单独进入指标快照。

### 指标查看

1. 应用维护进程内 HTTP 指标聚合；
2. 通过 `GET /debug/metrics/http` 返回 JSON 快照；
3. README 给出如何通过本地请求触发指标变化并查看结果。

## 接口或数据结构草案

- `config.Config`
  - `HTTPRateLimitEnabled bool`
  - `HTTPRateLimitRPS float64`
  - `HTTPRateLimitBurst int`
- `internal/platform/http`
  - `NewHTTPMetrics()`：创建进程内 HTTP 指标聚合器
  - `NewObservabilityMiddleware(...)`：包装稳定路由标识、访问日志与指标更新
  - `NewRateLimitMiddleware(...)`：提供进程内令牌桶限流
  - `requestIDMiddleware(...)`：负责请求 ID 注入与响应头回写
- 指标接口：`GET /debug/metrics/http`
- 请求头：`X-Request-ID`

## 错误处理与边界条件

- 对不存在或非法的 `X-Request-ID` 不报错，直接回退为服务端生成的新值，避免把请求关联能力变成新的脆弱点。
- 限流只作用于明确选定的高成本 / 高风险接口，避免对全部接口“一刀切”造成演示体验变差。
- 当前阶段不承诺真正的分布式 trace，也不伪装成完整 APM；文档中明确说明“请求 ID 是当前阶段的最小链路追踪锚点”。
- 当前阶段不做 Redis 分布式限流，避免为了单机 demo 过早引入外部设施；如未来多实例部署，再升级为共享存储实现。

## 中文注释计划

说明哪些代码位置必须写中文注释，以及要解释什么。

- `requestIDMiddleware`：解释为什么当前阶段把请求 ID 当作最小链路追踪锚点
- `RateLimitMiddleware`：解释为什么单进程项目先采用进程内令牌桶，以及键为什么优先绑定身份边界
- 路由注册处：解释登录、文档上传、文档重试、AI 问答为什么属于当前阶段的限流边界
