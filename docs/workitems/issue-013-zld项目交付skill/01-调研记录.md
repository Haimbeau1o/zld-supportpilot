# 调研记录

## 调研目标

把仓库上下文从 README 和 issue 中提炼为项目专属交付规则。

## 调研问题

- 哪些内容属于项目专属，不该写进通用 skill？
- 当前 issue 路线图里哪些关系是强依赖？
- 如何让项目 skill 直接为后续 issue 编排服务？

## 资料来源

| 来源 | 链接/位置 | 关注点 | 结论摘要 |
| --- | --- | --- | --- |
| `README.md` | 仓库根目录 | 项目定位与阶段目标 | 已有业务背景与模块划分基础 |
| `docs/coordination/当前Issue依赖与并发分析.md` | 本仓库 | 当前 issue 依赖关系 | 已经形成初步串并行结论 |
| 当前 GitHub issues #2~#14 | GitHub | 阶段划分与标题语义 | 已形成主线 / 并行 / 融合的语义层 |

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 不做项目 skill，只靠 README | 简单 | 后续调用时上下文不稳定 | 小型 demo | 否 |
| 把项目规则塞进通用 skill | 技能数量少 | 通用能力被污染 | 单项目短期仓库 | 否 |
| 独立项目 skill | 边界清晰，可长期维护 | 需要维护一份额外文档 | 长期项目 | 是 |

## 最终决策

采用独立项目 skill，专门封装 ZLD 的模块边界、路线图和融合策略。

## 决策理由

这样后续任何进入仓库的执行都能先获得项目上下文，不需要每次重新解释。
