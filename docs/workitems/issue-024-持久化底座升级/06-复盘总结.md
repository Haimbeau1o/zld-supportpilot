# 复盘总结

## 本次学到的内容

- 在“已有 memory 仓储 + service 边界稳定”的前提下，最稳妥的持久化升级方式是新增 adapter，而不是直接把数据库逻辑塞进 service
- 对象存储不一定要一步到位上 MinIO / S3；先用文件系统存储把接口、目录结构和恢复链路走通，更适合作为主线第一步
- 当 repository 接口未显式返回 `error` 时，数据库适配层必须至少保证“失败可见”，否则会出现更危险的静默数据丢失
- 测试分层很重要：配置与装配、对象存储、PostgreSQL 平台层、模块仓储应分别建 RED/GREEN 循环，避免把所有失败混在一起排查

## 关键取舍

- 选择 `database/sql` + `pgx stdlib`：保留标准库抽象，便于后续测试注入与驱动替换
- 选择 `sqlmock` 做 repository 最小契约测试：当前阶段优先验证 SQL 读写边界，不把外部 PostgreSQL 环境作为单元测试前置
- 选择文件系统存储原始文档：控制 issue 范围，把真实度集中在“可持久化恢复”，而不是外部对象存储编排
- 暂不处理队列持久化与任务恢复：当前后台处理队列仍是内存实现，后续 M4 融合阶段再评估是否补“重启后任务补偿”

## 遇到的问题

- SQL mock 链式调用的换行方式第一次写错，导致测试文件无法编译
- 文本替换工具误伤变量名，说明批量替换时需要优先选择更精确的上下文约束
- 知识库文档和任务模型里存在多个“未发生时间点”，如果 schema 直接使用 `NOT NULL`，落库语义会失真，因此补了 `NULL <-> time.Time{}` 映射
- 租户 ID 原本基于进程内自增，在持久化模式下会被服务重启击穿，这个问题在“从 memory 走向真实系统”的阶段必须尽早收敛

## 下次可优化点

- 为 PostgreSQL repository 增加更接近真实库的 integration test（可配合 docker compose 独立执行）
- 把 repository 接口逐步演进为显式返回 `error`，减少当前以 panic 暴露数据库异常的折中做法
- 为文件系统对象存储补充路径清理、限额控制和落盘审计信息
- 继续推进“处理任务补偿 / 重启恢复”机制，增强内用试运行稳定性
