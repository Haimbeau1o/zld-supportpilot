# 方案设计

## 设计目标

在不破坏现有模块化单体边界的前提下，为系统增加一套可切换的持久化底座：默认继续使用 memory 模式保证开发体验；显式启用 postgres 模式时，系统会建立数据库连接、自动初始化 schema，并把核心业务数据写入 PostgreSQL；文档原始内容则使用文件系统存储，保证文档重启后仍可恢复。

## 模块边界

- `internal/platform/config`
  - 增加持久化模式、PostgreSQL DSN、文档存储模式、文档存储目录等配置项
- `internal/platform/persistence`
  - 负责 PostgreSQL 连接、schema 初始化和公共 SQL 辅助能力
- `internal/module/identity`
  - 增加用户 / 成员关系的 PostgreSQL repository
- `internal/module/ticket`
  - 增加工单、评论、审计事件的 PostgreSQL repository
- `internal/module/knowledge`
  - 增加知识库、文档、处理任务、文档切块的 PostgreSQL repository
  - 增加文件系统对象存储实现
- `internal/app`
  - 根据配置决定实例化 memory 还是 postgres / filesystem adapter

## 数据流 / 时序

1. 应用启动读取配置；
2. 若 `APP_PERSISTENCE_MODE=memory`，保持当前行为不变；
3. 若 `APP_PERSISTENCE_MODE=postgres`，启动时建立数据库连接并执行 schema 初始化；
4. 各 service 继续只依赖 repository 接口，不感知底层实现；
5. 文档上传时，元数据落 PostgreSQL，原始文件落文件系统；
6. 文档处理任务与 chunk 结果落 PostgreSQL，重启后仍可被查询和检索。

## 接口或数据结构草案

- `config.Config`
  - `PersistenceMode string`
  - `PostgresDSN string`
  - `DocumentStorageMode string`
  - `DocumentStorageRoot string`
- `internal/platform/persistence`
  - `OpenPostgres(dsn string) (*sql.DB, error)`
  - `RunMigrations(db *sql.DB) error`
- `internal/module/knowledge`
  - `NewFileSystemObjectStorage(root string) *FileSystemObjectStorage`

## 错误处理与边界条件

- 开启 postgres 模式但未提供 DSN 时，应用启动必须显式报错，不能静默回退到 memory。
- 文件系统存储目录不存在时应自动创建，避免首次启动失败。
- schema 初始化使用幂等 SQL，避免重复启动报表已存在错误。
- 当前阶段不解决“处理中任务在重启后自动恢复执行”，只保证其状态与结果可持久读取。

## 中文注释计划

说明哪些代码位置必须写中文注释，以及要解释什么。

- `app.New()` 装配分支：解释为什么必须显式切换 memory / postgres，而不是隐式根据 DSN 自动判断
- PostgreSQL migration：解释当前阶段只做最小幂等 schema 初始化，而不引入完整 migration 框架
- 文件系统对象存储：解释为什么当前阶段先用 filesystem，而不是一步到位接 MinIO
- PostgreSQL repository 中的 upsert / 替换逻辑：解释为什么要保持当前 service 契约不变
