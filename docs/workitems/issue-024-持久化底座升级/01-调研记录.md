# 调研记录

## 调研目标

在尽量少破坏当前分层结构的前提下，为 `ZLD SupportPilot` 增加一套可讲清楚、可切换、可本地验证的持久化底座。

## 调研问题

- 当前 repository 抽象是否足够支撑 PostgreSQL 适配，而不回改 service 边界？
- PostgreSQL 连接与 schema 初始化应该放在 `module` 内部，还是 `platform` 装配层？
- 文档原始内容应该先接 MinIO，还是先做文件系统存储？
- 当前阶段要不要把处理任务与切块也一并持久化？

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 方案 A：直接把 service 改成依赖 `database/sql` | 实现快 | 打破当前分层，service 与存储耦合 | 快速原型 | 否 |
| 方案 B：保留 repository 抽象，新增 PostgreSQL adapter + 文件系统对象存储 | 最符合现有架构；可 memory / postgres 切换；便于测试 | 需要多写几层适配与 migration | 当前项目目标 | 是 |
| 方案 C：一步到位接 PostgreSQL + MinIO + Redis 持久队列 | 真实感最强 | 范围过大，容易拖慢 M4 主线 | 已准备大规模运维环境 | 否 |

## 最终决策

采用方案 B：保留现有 service 边界，在 repository 与 object storage 适配层补齐 PostgreSQL 和文件系统实现，并在 `app.New()` 中根据配置切换运行模式。

## 决策理由

- 这样最符合当前仓库“可演示、可讲清楚、逐步逼近真实系统”的节奏。
- PostgreSQL 解决“关键业务数据不丢失”，文件系统存储解决“原始文档可恢复”，已经足够支撑内部试运行。
- 当前阶段先不做队列与对象存储的完整生产化，避免 `#24` 范围膨胀成“基础设施重构”。
- 任务与 chunk 也应一并持久化，否则文档重启后无法维持 RAG 能力，业务上会形成断层。
