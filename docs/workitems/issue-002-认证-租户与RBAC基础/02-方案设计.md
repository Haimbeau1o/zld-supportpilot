# 方案设计

## 设计目标

以最小可用但可扩展的方式建立身份边界，使后续模块只关心“当前用户是谁、属于哪个租户、是否有权限”。

## 模块边界

- `internal/module/identity`：身份领域模型、角色权限、服务层、仓储接口、密码与令牌能力
- `internal/platform/http`：认证接口、鉴权中间件、请求上下文注入
- `internal/platform/config`：认证相关配置，如签名密钥和令牌 TTL
- `internal/app`：依赖装配

## 数据流 / 时序

1. 用户注册时，创建用户、组织和成员关系，并分配默认角色
2. 用户登录时，校验邮箱和密码，签发访问令牌
3. 请求进入受保护路由时，从 Header 中解析令牌
4. 鉴权中间件将用户 ID、租户 ID、角色和权限注入上下文
5. 后续模块根据上下文判断是否允许执行操作

## 接口或数据结构草案

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`

核心模型草案：

- `User`
- `Organization`
- `Membership`
- `Role`
- `Permission`
- `IdentityContext`

## 错误处理与边界条件

- 重复邮箱注册应返回明确错误
- 无效密码与不存在用户应统一成安全错误语义，避免泄露过多信息
- 令牌无效、过期或签名错误时应直接拒绝访问
- 默认角色分配要固定，并在代码中写中文注释说明原因
- 鉴权上下文中必须明确区分“未登录”和“无权限”两类错误

## 中文注释计划

以下位置必须写中文注释：

- 默认角色和默认权限的分配逻辑
- 令牌签发与校验的安全边界
- 鉴权中间件如何把身份上下文传给后续模块
- 权限校验为什么采用角色到权限映射，而不是直接写死角色判断
