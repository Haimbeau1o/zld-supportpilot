# 复盘总结

## 本次学到的内容

- 认证基础阶段最重要的不是“功能多”，而是先稳定身份边界、租户上下文与权限来源
- HTTP 层采用显式依赖注入后，既能保留骨架的轻量入口，也能让测试直接走真实业务链路
- 把权限集合在服务端按角色重建，比把完整权限列表直接塞进令牌更容易保持单一真相来源

## 关键取舍

- 选择 JWT Access Token，而不是更重的 Session / Redis 方案
- 选择 interface-first + 内存适配，先稳定结构，再考虑数据库实现
- 保留 `NewMux`，新增 `NewMuxWithDependencies`，用最小改动实现路由装配与测试可控性

## 遇到的问题

- 初始 HTTP 骨架没有业务依赖注入位点，若直接在 HTTP 层内部 new 服务，会破坏分层边界
- 初始配置没有认证参数，导致应用装配无法稳定构造令牌能力
- `me` 接口需要既拿到身份，又避免令牌与权限表双写漂移，因此最终采用“令牌存角色，权限服务端重建”的做法

## 下次可优化点

- 增加刷新令牌、注销与签名密钥轮换能力
- 在身份基础稳定后，为用户、组织、成员关系补数据库持久化实现
- 为受保护路由继续补“已登录但无权限”的 HTTP 级测试

## 对后续 Issue 的影响

- `#3` 与 `#5` 将直接复用本 Issue 产出的身份上下文、中间件与权限入口
- 由于身份边界已稳定，后续工单主流程与知识库主流程可以在受保护路由之上并行推进
- 如果后续出现模块融合问题，应优先在融合 Issue 中检查权限命名、上下文字段和路由接线是否一致
