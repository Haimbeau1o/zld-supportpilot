# 实施计划

## 目标拆解

| 步骤 | 工作项 | 预期输出 | 依赖 | 是否可并行 |
| --- | --- | --- | --- | --- |
| 1 | 定义身份领域模型与权限映射 | `model.go` `permission.go` | 无 | 否 |
| 2 | 定义仓储接口与服务层 | `repository.go` `service.go` | 步骤 1 | 否 |
| 3 | 增加密码与令牌能力 | `password.go` `token.go` | 步骤 2 | 部分可并行 |
| 4 | 增加 HTTP 处理器和鉴权中间件 | `auth_handler.go` `auth_middleware.go` | 步骤 2~3 | 否 |
| 5 | 装配配置与依赖，补充 README 和验证 | `app.go` `config.go` `README.md` | 步骤 4 | 否 |

## 执行顺序

先稳定领域模型和权限映射，再做服务层，再做令牌与中间件，最后暴露 HTTP 接口并更新文档。

## 风险点

- 过早引入复杂 IAM 能力会拖慢后续工单与知识库开发
- 如果角色和权限命名不稳定，后续模块会频繁返工
- 如果只写角色判断不抽象权限映射，后续扩展会很痛苦

## 联调点 / 融合点

- 后续 `ticket` 与 `knowledge` 模块都依赖 `IdentityContext`
- 需要在 `#3` 与 `#5` 开工前固定好租户上下文和权限校验入口
- 详细分解见：`docs/plans/2026-03-07-auth-rbac-foundation-implementation-plan.md`
