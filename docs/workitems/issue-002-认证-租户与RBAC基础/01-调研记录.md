# 调研记录

## 调研目标

为 `ZLD SupportPilot` 选择一套既适合当前 MVP、又能支撑后续模块扩展的认证与权限基础方案。

## 调研问题

- 当前阶段更适合 Session、JWT，还是不透明 Token？
- RBAC 应该先做角色到权限映射，还是直接做更细的 ABAC？
- 数据持久化应该一步到位做数据库，还是先做接口优先的内存适配？

## 资料来源

| 来源 | 链接/位置 | 关注点 | 结论摘要 |
| --- | --- | --- | --- |
| 当前项目 README 与 issue #2 | 本仓库 / GitHub | 基础能力的定位 | 目标是建立统一身份边界，而不是一次做完全部 IAM 能力 |
| 现有代码骨架 | `cmd/` `internal/` | 当前技术栈与依赖 | 目前是标准库 HTTP 骨架，适合先做 interface-first 设计 |
| `iam/` 参考项目 | 上级仓库参考目录 | 组织、成员、权限模型经验 | 可以借鉴概念，但不直接搬复杂结构 |

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| Session + Redis | 服务端可控，撤销方便 | 增加状态管理复杂度 | Web 单体后台 | 否 |
| JWT Access Token | 适合 API，后续扩展容易 | 需要自己管理签发与校验边界 | API 驱动服务 | 是 |
| 不透明 Token | 实现简单 | 后续扩展和调试可读性较弱 | 小型内部系统 | 否 |
| 角色枚举，不做权限映射 | MVP 快 | 后续扩展权限控制困难 | 极小项目 | 否 |
| 角色 -> 权限映射 RBAC | 平衡复杂度与扩展性 | 需要维护权限表 | 多模块系统 | 是 |
| 直接做 ABAC | 很灵活 | 过早复杂化 | 权限特别复杂的系统 | 否 |
| 直接做数据库持久化 | 更真实 | 当前代码骨架尚未建立数据层 | 数据层已稳定 | 暂缓 |
| 先做接口优先 + 内存适配 | 快速建立边界，便于 TDD | 后续还要接数据库适配 | 当前阶段 | 是 |

## 最终决策

当前阶段采用：`JWT Access Token + 角色到权限映射的 RBAC + interface-first 的内存适配实现`。

## 决策理由

这样可以先稳定身份边界和权限模型，支持后续工单与知识库主流程开发；同时避免在认证基础阶段把数据库和高级 IAM 特性一次性做得过重。
