# 复盘总结

## 本次实际收获

- 学会把“工单主流程”和“工单协作/审计”拆成两个渐进式子模块，降低一次性建模过重的风险。
- 学会在服务层自动沉淀审计事件，而不是依赖调用方手工补日志。
- 学会处理评论可见性、内部备注权限和时间线聚合输出。
- 学会通过 worktree + TDD + 分层测试，把一个看似简单的需求做成可复述、可验证、可扩展的后端交付过程。

## 本次关键取舍

- 没有为评论再单独生成审计事件，而是让评论本身直接进入时间线；这样避免重复展示，同时时间线语义更清晰。
- 没有在 HTTP 层拼装时间线，而是坚持把聚合和过滤逻辑放在服务层，减少权限漂移风险。
- 先继续使用内存仓储，不提前引入数据库迁移，确保本阶段重心仍然是业务边界和接口设计。

## 踩坑与修正

- 初版设计草案里曾考虑为评论补 `comment_added` / `internal_note_added` 审计事件，但实现前重新审视后发现会导致时间线重复，因此在落地时收敛为“评论实体直接作为时间线条目”。
- HTTP 层新增测试首次全部返回 `404`，这一步很有价值：它证明测试先准确卡住了缺失接口，而不是后验补测试。
- 如果 app 层不显式接入评论仓储和审计仓储，就会出现“服务可编译、路由可注册、但能力实际上没启用”的隐蔽问题，因此补了 `internal/app` 集成测试兜底。

## 后续可扩展项

- 评论编辑 / 删除与审计追踪
- @提及、通知和订阅
- 附件上传与评论关联
- AI 摘要、回复草稿和 AI 操作轨迹接入统一时间线
- 持久化仓储（PostgreSQL）与分页查询

## 对并发协作的启发

- `#4` 适合在 `#3` 合并后立即并行推进，因为它只依赖工单主流程，不依赖 RAG 或 AI 子系统。
- `#4` 不会阻塞 `#7` / `#8`，因此应尽早完成，为后续“AI 参与工单协作”提供稳定承接点。
- 后续如果同时推进附件、通知、AI 协作记录，应该再开一个融合 issue，专门统一时间线数据结构、接口契约和联调策略。
