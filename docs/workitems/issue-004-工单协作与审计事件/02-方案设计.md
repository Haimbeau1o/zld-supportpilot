# 方案设计

## 设计目标

在保留 `#3` 工单主流程稳定性的基础上，为 ticket 模块增加评论、内部备注和审计事件能力。所有关键动作都通过服务层统一记录，保证权限、租户边界和时间线语义不漂移。

## 模块边界

- `internal/module/ticket`
  - 扩展 `Ticket` 相关协作模型
  - 定义 `TicketComment`、`TicketAuditEvent`、时间线查询能力
  - 在 `CreateTicket`、`AssignTicket`、`TransitionTicketStatus` 中统一记录审计事件
  - 在 `AddTicketComment` 中统一处理评论类型与可见性边界
- `internal/platform/http`
  - 新增评论写入接口和时间线查询接口
  - 仅负责请求解析、调用服务和错误映射，不在 HTTP 层自行拼装时间线
- `internal/app`
  - 装配扩展后的 ticket service 与协作仓储

## 数据流 / 时序

1. 用户访问工单协作接口，首先通过鉴权中间件进入带身份上下文的服务层。
2. 追加评论 / 内部备注时，服务层先校验工单访问权限，再校验备注类型权限。
3. 评论写入成功后，只生成一条评论记录；不再额外生成 `comment_added` / `internal_note_added` 审计事件，避免时间线出现“同一次评论被展示两次”的重复条目。
4. 工单创建、指派变更和状态流转成功后，同步追加 `created`、`assignment_changed`、`status_changed` 审计事件。
5. 查询时间线时，服务层统一返回按时间排序的评论与审计事件组合结果，并对终端用户过滤内部备注。

## 接口或数据结构草案

新增模型：

- `TicketComment`
- `TicketCommentType`（`comment` / `internal_note`）
- `TicketAuditEvent`
- `TicketAuditEventType`（`created` / `assignment_changed` / `status_changed`）
- `TicketTimelineItem`

新增接口：

- `POST /api/v1/tickets/{id}/comments`
- `GET /api/v1/tickets/{id}/timeline`

评论请求体：

```json
{
  "type": "comment",
  "content": "请先确认 VPN 客户端版本。"
}
```

时间线响应条目核心字段：

```json
{
  "item_type": "audit_event",
  "audit_event_type": "created",
  "content": "工单已创建"
}
```

## 错误处理与边界条件

- 空评论内容直接返回 400。
- 不支持的评论类型直接返回 400。
- 终端用户可追加普通评论，但不能写内部备注。
- 内部备注只对具备工单写权限的角色可见。
- 时间线查询必须过滤租户边界，且对终端用户隐藏内部备注。
- 指派和状态流转的审计记录由服务层自动生成，避免依赖调用方记得额外写日志。
- 当应用未装配协作仓储时，评论与时间线接口返回“能力未启用”，避免静默失败。

## 中文注释计划

以下位置必须写中文注释：

- 为什么审计事件在写操作发生时显式落地，而不是查询时再推导
- 为什么内部备注对终端用户不可见
- 为什么评论 / 审计时间线统一从服务层输出，避免 HTTP 层自行拼装导致权限漂移
- 为什么指派与状态变更需要自动记录审计事件

## 实际落地说明

与初版草案相比，最终实现有一处关键收敛：没有为“公开评论 / 内部备注”单独追加审计事件，而是直接把评论实体作为时间线条目的一类来源输出。这样既保留了完整协作痕迹，又避免了同一动作在时间线中重复展示两次。
