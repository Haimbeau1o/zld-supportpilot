# 任务卡

## 基本信息

- Issue 编号：#6
- Issue 标题：并行：异步文档处理流水线
- 类型：并行
- 所属阶段：M2 - 工单与知识库

## 背景与问题

当前知识库链路已经具备知识库创建、文档上传和原始文件存储能力，但文档解析、切块和索引仍未落地。如果把这些处理直接放到上传 API 中，会导致接口响应时间不可控，也会让失败重试、状态追踪和后续 RAG 检索边界变得模糊。

## 目标

在不破坏 #5 上传主链路的前提下，引入最小可用的异步文档处理流水线，让系统具备“上传完成即入队、后台处理、失败可追踪、人工可重试”的能力，并为 #7 的检索与回答接口稳定输出切块与索引边界。

## 范围

### 包含

- 文档处理任务模型与状态流转
- 解析、切块、索引三段式处理边界
- 文档处理任务仓储与内存队列/worker 适配
- 上传后异步入队
- 失败状态沉淀与人工重试入口
- 任务查询接口、必要的文档处理元数据返回
- 对应测试、中文注释和工作文档沉淀

### 不包含

- 真实 PDF/OCR 解析能力
- 真实向量数据库接入
- 检索召回与回答生成接口
- 多节点分布式消息队列
- 复杂优先级调度、延迟队列和批处理编排

## 前置依赖

- #5 主线：知识库与文档上传

## 并发性判断

- 是否可独立并行：是
- 如果不能并行，阻塞点是什么：不能早于 #5，因为需要复用文档上传后的元数据和原始存储边界
- 如果可以并行，可与哪些 Issue 同步推进：可与 #4 并行推进；不应与 #7 并行开发，因为 #7 依赖本 issue 输出的切块/索引边界
- 是否需要后续融合 Issue：是，后续需与 #7 做检索链路融合

## 验收标准

- 文档上传接口不执行耗时处理，但会为文档创建异步处理任务
- 文档处理可沿“解析 -> 切块 -> 索引”推进，状态可查询
- 失败任务会沉淀失败原因，且支持人工重试
- 处理链路的边界足够清晰，#7 可以直接复用切块和索引抽象
