# 调研记录

## 调研目标

明确 #6 在当前仓库中的最佳落点：既要把上传 API 与耗时处理解耦，又要为后续 RAG 检索保留稳定的解析、切块和索引边界。

## 调研问题

- 现有 #5 上传链路中，文档元数据与原始文件分别落在哪一层？
- 异步处理是挂在 `knowledge.Service` 内部，还是独立成处理器组件更合适？
- 失败追踪是只挂在 `Document` 字段上，还是需要显式任务实体？
- 为 #7 预留边界时，是否需要现在就落 chunk/index 抽象？

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 方案 A：上传接口内同步解析/切块/索引 | 实现简单、调用链短 | API 变慢、失败难追踪、无法体现真实后端异步架构能力 | Demo 一次性脚本 | 否 |
| 方案 B：上传后创建处理任务，由内存队列和后台 worker 处理 | 能体现真实后端分层；失败与重试可沉淀；后续可替换为真实消息队列 | 需要增加任务模型、队列和轮询测试 | 当前仓库阶段，且需要为 #7 铺路 | 是 |
| 方案 C：直接接入 Redis Stream / Kafka | 架构更接近生产 | 对当前项目体量过重；会把重点从业务边界转成基础设施搭建 | 已有外部基础设施和部署环境 | 否 |

## 最终决策

采用方案 B：在 `knowledge` 模块内引入显式处理任务模型、解析/切块/索引边界、内存队列与后台 worker，并通过 HTTP 暴露任务查询和重试入口。

## 决策理由

- 它最符合当前项目“先稳定边界、后替换底层实现”的演进策略。
- 显式任务模型比只在 `Document` 上堆字段更利于学习和展示：能清楚表达一次处理的阶段、状态、错误和重试次数。
- 先定义 chunk/index 边界，即使当前只是内存实现，也能显著降低 #7 的返工成本。
- 用 Go channel + goroutine 落一个单进程 worker，既能体现 Go 并发能力，又不会过早把项目复杂度推到分布式基础设施层面。
