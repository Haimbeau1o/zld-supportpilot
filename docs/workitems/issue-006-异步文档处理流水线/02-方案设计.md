# 方案设计

## 设计目标

在保持上传 API 快速返回的前提下，把知识文档的重处理链路拆成“原始文档存储”和“后台文档处理”两部分：上传只负责写入元数据和原始文件，后台 worker 再完成解析、切块和索引。这样既能满足 #6 的异步诉求，也能给 #7 的检索能力提供稳定输入。

## 模块边界

- `internal/module/knowledge/model.go`
  - 扩展 `Document` 处理元数据
  - 增加 `DocumentProcessingTask`、`DocumentChunk` 等领域模型
- `internal/module/knowledge/repository.go`
  - 增加处理任务仓储与 chunk 仓储接口
- `internal/module/knowledge/storage.go`
  - 为对象存储补充读取能力，支持后台重新拉取原始文档
- `internal/module/knowledge/processing.go`
  - 定义 parser、chunker、indexer、dispatcher、worker 等抽象
- `internal/module/knowledge/memory_*.go`
  - 提供内存任务仓储、chunk 仓储、队列、解析器、切块器和索引器
- `internal/platform/http/knowledge_handler.go`
  - 增加任务查询和重试接口
- `internal/app/app.go`
  - 装配后台 worker，并在应用关闭时回收

## 数据流 / 时序

1. 用户调用上传接口，服务层完成权限校验、原始文件存储和文档元数据写入。
2. 文档保存成功后，服务层创建一条 `DocumentProcessingTask`，初始状态为 `queued`，阶段为 `parse`。
3. 后台 worker 从队列中取出任务，先把任务和文档状态推进到 `processing`。
4. `parser` 从对象存储读取原始文件并转成可切块的纯文本结构。
5. `chunker` 按固定大小和段落边界生成 `DocumentChunk` 列表。
6. `indexer` 将 chunk 写入内存索引/仓储，为后续 #7 检索复用。
7. 成功时，任务标记为 `succeeded`，文档标记为 `ready`；失败时，任务和文档都记录错误原因，文档转为 `failed`。
8. 运维或业务方可通过重试接口重新发起处理；新任务会带上新的 attempt 序号。

## 接口或数据结构草案

新增核心模型：

- `DocumentProcessingTask`
- `ProcessingTaskStatus`
- `ProcessingStage`
- `DocumentChunk`
- `ParsedDocument`

新增服务能力：

- `ListDocumentProcessingTasks(actor, documentID)`
- `RetryDocumentProcessing(actor, documentID)`
- `ProcessTask(ctx, taskID)`

新增 HTTP 接口：

- `GET /api/v1/knowledge/documents/{id}/tasks`
- `POST /api/v1/knowledge/documents/{id}/retry`

## 错误处理与边界条件

- 上传成功但入队失败时，不回滚原始文档；而是把文档标为 `failed` 并记录失败任务，体现“上传”和“处理”已解耦。
- 只有具备知识库管理权限的角色可执行重试；只读角色可以查看任务状态，但不能触发处理。
- 处理任务必须按阶段推进：解析失败不能进入切块，切块失败不能进入索引。
- 重试不是原任务就地覆盖，而是创建新任务记录，保留历史轨迹，方便教学和排障。
- 当前只做单进程内存队列，不解决多实例抢占和分布式幂等；这些能力放到后续演进。

## 中文注释计划

以下位置必须写中文注释：

- 为什么上传 API 只负责“存储 + 入队”，而不负责同步解析
- 为什么处理失败不回滚文档，而是沉淀任务记录与失败状态
- 为什么切块和索引在当前阶段先保留抽象边界，而不是直接耦合到 RAG 接口
- 为什么 worker 使用 channel + context 管理生命周期，而不是裸 goroutine 无边界运行
- 为什么重试采用“创建新任务”而不是覆盖旧任务
