# 实施计划

## 实施顺序

1. 先补 knowledge candidate 领域模型与 service 的 RED 测试
2. 实现 memory / postgres repository 与 schema
3. 实现候选创建、列表、审核 API
4. 接通 app 装配与文档处理联动验证
5. 更新 README、验证记录与 issue 工作包

## 串并行判断

### 串行部分

- 候选模型与 repository
- service 业务规则
- HTTP API
- app 装配与联调

### 可并行部分

- 工作包文档沉淀
- README 补充
- sqlmock 测试细化

### 融合点

- 审核通过后必须验证生成文档确实进入知识处理链路
- 最终要验证候选知识可被后续问答命中

## 风险点

- 当前 ticket 缺少专门的解决结论字段
- 若候选内容完全自动生成，知识质量不可控
- 若不复用现有知识处理链路，会造成体系分叉

## 风险应对

- 采用人工整理型候选
- 审核通过后统一走 markdown 文档入库
- 用测试验证“候选审批 -> 文档处理 -> 问答命中”全链路
