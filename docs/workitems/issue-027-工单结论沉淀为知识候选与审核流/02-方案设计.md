# 方案设计

## 方案选型

### 方案 A：从已解决工单自动提炼知识内容

优点：

- 使用方最省操作

缺点：

- 当前 ticket 模型没有稳定的“最终解决结论”字段
- 纯靠时间线拼接很容易生成低质量知识
- 真实业务里通常仍需要人工审核和整理

### 方案 B：从已解决工单创建“人工整理型知识候选”并审核入库（推荐）

优点：

- 与真实服务台场景更贴近
- 不需要大改 ticket 主模型
- 审核通过后可直接复用现有知识处理链路

缺点：

- 需要 agent 多做一次整理提交

### 方案 C：要求工单在 resolve 时必须填写解决结论，再自动转候选

优点：

- 结论来源更结构化

缺点：

- 需要改 ticket 流转契约
- 影响面更大，不适合作为当前并行 issue 的最小实现

## 推荐结论

采用方案 B：只允许从 `resolved` 工单生成知识候选，候选内容由 agent 在提交时人工整理，审核通过后系统生成 markdown 文档并进入现有知识处理流水线。

## 领域模型

### 新增模型

- `KnowledgeCandidateStatus`
  - `pending_review`
  - `approved`
  - `rejected`
- `KnowledgeCandidate`
- `ReviewKnowledgeCandidateAction`
  - `approve`
  - `reject`

## 服务设计

在 `knowledge` 模块新增三类能力：

### 1. 创建候选

`CreateKnowledgeCandidateFromTicket(actor, input)`

输入：

- `ticket_id`
- `knowledge_base_id`
- `title`
- `summary`
- `content`

规则：

- 只能对 `resolved` 工单创建候选
- 调用方需具备知识写权限
- 候选创建后状态为 `pending_review`

### 2. 候选列表

`ListKnowledgeCandidates(actor, input)`

用途：

- 支持后台审核视图
- 当前阶段仅做列表，不做复杂过滤后台

### 3. 审核候选

`ReviewKnowledgeCandidate(actor, input)`

#### `approve`

- 候选状态改为 `approved`
- 生成 markdown 文档内容
- 创建 `knowledge.Document`
- 保存到对象存储
- 触发现有处理流水线
- 回写 `approved_document_id`

#### `reject`

- 候选状态改为 `rejected`
- 回写审核人和审核意见
- 不进入文档处理链路

## HTTP API

### 创建候选

- `POST /api/v1/knowledge/candidates`

请求体：

```json
{
  "ticket_id": "ticket-1",
  "knowledge_base_id": "kb-1",
  "title": "VPN 691 错误排查",
  "summary": "通过重置账号拨号权限恢复",
  "content": "现象、原因、处理步骤、验证结果..."
}
```

### 列表

- `GET /api/v1/knowledge/candidates?knowledge_base_id=kb-1`

### 审核

- `POST /api/v1/knowledge/candidates/{id}/review`

请求体：

```json
{
  "action": "approve",
  "comment": "内容可入库"
}
```

## 关键取舍

- 当前阶段不引入 LLM 自动总结，保持候选质量可控
- 当前阶段不做复杂运营后台，只保留“列表 + 审核”最小视图
- 当前阶段用 markdown 文档承接知识候选入库，最大化复用现有对象存储与处理链路
