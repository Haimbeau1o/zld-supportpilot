# 调研记录

## 调研目标

确认 `#27` 应落在哪个模块，如何复用既有 ticket / knowledge 能力，以及什么样的最小方案既真实可用，又不会过度扩展现有模型。

## 调研范围

- `internal/module/ticket/*`
- `internal/module/knowledge/*`
- `internal/platform/http/ticket_handler.go`
- `internal/platform/http/knowledge_handler.go`
- `internal/app/app.go`
- `internal/platform/persistence/schema.sql`

## 关键发现

### 1. 当前 ticket 模型有“已解决”状态，但没有专门的结论摘要字段

现有工单模型与状态机已经支持：

- `open`
- `in_progress`
- `resolved`
- `closed`

但 `resolved` 只表示状态完成，并不强制沉淀“最终解决结论”。如果直接从现有工单和时间线全自动提炼知识文档，内容质量会很不稳定。

### 2. 当前知识处理链路已经完整，最值得复用的是“文档入库 + 异步处理”能力

`knowledge.Service.UploadDocument` 已经具备：

- 创建文档元数据
- 保存原始内容到对象存储
- 创建处理任务
- 驱动解析 / 切块 / 索引

因此 `#27` 没必要新造一套知识入库链路。更合适的做法是：审核通过时把知识候选转成一份生成型 markdown 文档，再复用现有处理流水线。

### 3. `knowledge.ObjectStorage` 已支持直接保存字节内容

这意味着系统不仅能接受用户上传文件，也能接受“系统内部生成的文档内容”。这一点非常关键，它让“审核通过 -> 生成文档 -> 入处理链路”变得自然。

### 4. `#27` 更适合放在 knowledge 模块，而不是 ticket 模块

虽然入口来自工单，但最终产物和生命周期属于知识域：

- 候选状态
- 审核动作
- 入库结果
- 后续被问答命中

因此推荐把知识候选放在 `internal/module/knowledge` 中，并通过 ticket 读取边界获取已解决工单上下文。

### 5. 最小真实方案不应追求“全自动生成”，而应保留人工整理环节

如果现在就要求系统从工单自动输出高质量知识结论：

- 需要新增 resolution summary 机制，或
- 需要引入 LLM 生成与质检逻辑

这会把 `#27` 拉得过重。更符合当前阶段的做法是：

- 只允许从 `resolved` 工单创建候选
- 创建时由 agent 人工填写标题 / 摘要 / 正文
- 审核通过后再正式入库

## 设计推论

- `#27` 推荐采用“人工整理 + 审核入库”的最小真实闭环
- 候选应新增独立状态模型：`pending_review / approved / rejected`
- 审核通过后应生成 markdown 文档并复用现有文档处理链路
- 后续 `#28` 可以再把 `#26` 的反馈和 `#27` 的知识候选回流策略融合起来

## 结论

推荐方案：在 `knowledge` 模块中新增知识候选能力，并通过 ticket 只读边界接入“已解决工单”，用最小人工整理闭环保证候选质量与业务真实性。
