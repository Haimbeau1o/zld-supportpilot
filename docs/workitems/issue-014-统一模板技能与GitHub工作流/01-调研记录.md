# 调研记录

## 调研目标

把方法层的多个产出统一为一套可执行规范，而不是分散的文档集合。

## 调研问题

- 哪些内容必须仓库内保留，哪些适合放进 skill？
- GitHub issue / PR 模板如何与 docs/workitems 对齐？
- 融合 issue 如何避免只做“文档汇总”？

## 资料来源

| 来源 | 链接/位置 | 关注点 | 结论摘要 |
| --- | --- | --- | --- |
| `docs/templates/*` | 本仓库 | 每个 issue 的固定交付结构 | 7 件套已定义 |
| `skills/learning-rd-workflow/` | 本仓库 | 通用方法层规则 | 提供固定输出与并发性分析法 |
| `skills/zld-supportpilot-delivery/` | 本仓库 | 项目上下文与路线图规则 | 提供模块边界与当前依赖结论 |
| GitHub issue / PR 模板 | 本仓库 .github | 中文协作入口 | 需与模板和 skill 保持一致 |

## 候选方案比较

| 方案 | 优点 | 缺点 | 适用条件 | 是否采用 |
| --- | --- | --- | --- | --- |
| 模板、skill、GitHub 各自维护 | 改动快 | 很快产生术语漂移 | 短期试验 | 否 |
| 通过融合 issue 统一收口 | 可验证一致性 | 需要额外一步整理 | 长期维护项目 | 是 |

## 最终决策

采用融合 issue 统一收口模板、skill 和 GitHub 工作流。

## 决策理由

如果没有融合步骤，后续很容易出现仓库文档、skill 和 GitHub 模板三套标准不一致。
