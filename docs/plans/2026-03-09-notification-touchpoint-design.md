# #29 企业通知与待办触达设计

## 背景

`#29` 的目标不是做一个完整消息中心，而是在 M4 内测阶段补齐最小可用的“触达能力”。当前系统已经有：

- 工单创建、分派、状态流转
- AI 统一受理与升级建单
- 知识回流与审核

但如果没有通知，处理方只能靠手工刷新列表，系统虽然能“跑通流程”，却还不像真正被内部团队使用的业务系统。

## 目标

本次只做最小闭环所需能力：

- 提供可替换的通知抽象
- 落地两种渠道：邮件、Webhook
- 在三类核心事件上触发通知：
  - 工单分派
  - 工单状态变更
  - AI 升级为人工跟进
- 保证通知失败不会阻塞主业务流程

## 设计原则

### 1. 通知是业务旁路，不反向污染主流程

通知能力需要依附业务动作，但不能反过来把工单、AI 服务变成“消息中心协调器”。因此采用“领域服务发布事件、通知模块负责投递”的方式。

### 2. 先稳定边界，再扩展渠道

当前阶段先稳定：

- 通知事件模型
- 渠道接口
- 邮件 / Webhook 两个实现

飞书等 IM 渠道后续可以通过 Webhook 或新增 Channel 平滑接入。

### 3. 最小权限与最小依赖

邮件收件人只解析当前动作直接相关的用户（如 requester / assignee），不引入额外的组织通讯录系统；Webhook 则面向系统集成，直接输出结构化事件。

## 方案概览

### 方案选择

本次采用：**独立通知模块 + 业务服务内最佳努力发布**。

对比：

1. **直接在 handler 内发送通知**
   - 优点：改动点少
   - 缺点：HTTP 层和业务层职责混乱，后续其他入口容易漏通知

2. **通知模块 + 领域服务发布事件（采用）**
   - 优点：挂点稳定，后续 CLI / 定时任务 / 其他入口复用同一业务逻辑时仍能触发通知
   - 缺点：需要补一个通知抽象和依赖注入

3. **完整事件总线 / MQ**
   - 优点：最强扩展性
   - 缺点：当前项目阶段过重，不符合 YAGNI

## 模块划分

### `internal/module/notify`

新增通知模块，承担：

- 定义通知事件模型
- 定义渠道接口
- 负责收件人解析
- 执行多渠道投递
- 汇总但不强制上抛投递失败

### 业务挂点

- `ticket.Service.AssignTicket()`：发布“工单分派通知”
- `ticket.Service.TransitionTicketStatus()`：发布“工单状态变更通知”
- `ai.Service.HandleUnifiedIntake()` / `SubmitAnswerFeedback()`：在 AI 升级建单时发布“升级通知”

## 收件人与渠道策略

### 邮件

- 通过用户目录按 `userID` 解析邮箱
- 默认通知与当前工单直接相关的人：
  - 分派：新 assignee + requester
  - 状态变更：requester + assignee（若存在）
  - AI 升级：requester
- 本地与演示环境使用日志型 mail sender，确保无需额外 SMTP 依赖也可验证流程

### Webhook

- 对配置的 URL 列表逐个发送结构化 JSON 事件
- 失败按渠道维度记录并忽略，不影响主业务返回
- 后续飞书 / 企业微信等可通过 webhook 适配

## 故障处理

### 最佳努力原则

通知模块允许渠道失败，但不会让：

- 指派失败
- 状态流转失败
- AI 升级失败

也就是说：**业务成功优先，通知做旁路保障**。

### 失败可观察性

当前阶段通过：

- 返回聚合 error 给调用方（业务层选择忽略）
- 日志输出失败信息

后续 `#30` 可继续补审计留痕和运营统计。

## 测试策略

### 模块测试

- 通知服务能对多个渠道执行投递
- 单个渠道失败不会阻断其他渠道
- 邮件渠道能按 userID 解析收件人
- Webhook 渠道能正确发送结构化事件

### 业务测试

- `ticket`：分派 / 状态变更时发布通知
- `ai`：升级建单时发布通知
- 通知失败时业务动作仍成功

## 预期产出

完成后，项目会具备更真实的内部使用感：

- 坐席被分派后能收到提醒
- 请求人能感知工单状态变化
- AI 无法自助解决时，系统能把升级动作主动推给外部集成或内部待办系统
