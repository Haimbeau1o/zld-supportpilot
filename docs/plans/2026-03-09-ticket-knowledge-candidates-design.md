# 工单知识候选设计说明

## 设计目标

为 `ZLD SupportPilot` 增加“已解决工单沉淀为知识候选”的业务能力，并在不改动当前工单主流程契约的前提下，复用现有知识处理链路完成审核入库。

## 核心判断

当前系统已经有两个成熟基础：

1. ticket 侧：有状态流转、时间线、评论和审计事件
2. knowledge 侧：有文档对象存储、异步处理、切块、索引和问答能力

`#27` 的设计关键，是不要额外发明第三条“知识入库链路”，而是把“知识候选”作为 knowledge 域内的审核前状态，并在审核通过后转成正式文档进入既有流水线。

## 推荐方案

采用“人工整理型知识候选”：

- 候选只允许从 `resolved` 工单创建
- 创建时由 agent 明确填写标题、摘要、正文
- 审核通过后生成 markdown 文档并进入现有 processing pipeline
- 审核驳回则只保留候选记录和审核意见

## 不推荐方案

### 全自动从工单时间线生成知识

风险太高：当前 ticket 模型没有稳定 resolution summary，纯靠拼时间线会让知识质量波动很大。

### 在工单 resolve 流程强制新增结论字段

会扩大改动面，并把一个并行 issue 变成 ticket 主流程重构，不适合当前阶段。

## 预期收益

- 知识库可以持续吸收一线工单处理经验
- 审核机制保证知识质量不失控
- 后续 `#28` 可把知识候选与 AI 反馈回流统一到更完整的业务闭环中
